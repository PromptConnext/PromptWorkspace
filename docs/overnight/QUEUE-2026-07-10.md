## Update — verified apps/cloud against real local Supabase, fixed 5 latent bugs

At the user's instruction ("Can you use local Supabase to implement"),
installed the Supabase CLI, started a real local stack (`supabase start` —
Postgres + GoTrue + PostgREST, scoped to `apps/cloud/supabase/` with remapped
ports to avoid colliding with an unrelated already-running local Supabase
instance on this machine), applied all migrations, and ran `apps/cloud` with
`DATA_BACKEND=supabase AUTH_MODE=supabase` for the first time ever — every
prior verification (this session and all prior M1–M7 work) only exercised
the in-memory backend + stub auth.

This surfaced **5 real, previously-unreachable bugs**, each found by an
actual failing request against real infrastructure, not inspection:

1. JWT verification was HS256-only; Supabase Auth issues asymmetric ES256
   tokens by default now — a genuinely valid token was rejected outright.
2. `for_user()` (forwards the caller's JWT so RLS applies) was dead code —
   no route ever called it. RLS was never actually enforced by any real
   request, ever, despite the M2 design docs describing it as "defense in
   depth."
3. No migration ever `GRANT`ed base table privileges to `authenticated` —
   RLS policies existed but were unreachable (Postgres checks the grant
   before RLS runs). Hosted Supabase does this automatically at project
   creation, masking the gap.
4. The first admin-membership insert for a new workspace could never
   satisfy its own RLS policy (`pz_is_admin` — no admin exists yet).
   **Workspace creation was unreachable under real RLS enforcement** — this
   is the actual keystone feature of M2, and it would have been broken the
   moment #2 was fixed, had #4 not been fixed alongside it.
5. `pz_invitations` had RLS enabled nowhere at all — after fixing #3's
   grants, this became a real hole (any authenticated user could read/
   modify any workspace's invitations) rather than an accidental lockout.

All fixed (migrations 0006–0008, `app/dependencies.py`, `app/config.py`,
`app/db/supabase_repository.py`), verified live with two real signed-up
Supabase users through the full workspace → project → invite → accept →
cross-user-visibility flow, plus a correct 404 (not a leak) for an
unrelated workspace. Full details and reasoning are in each migration
file's own comments and the commit message (`fa55d56`). All 50 existing
tests still pass (one, `test_health`, needed its hardcoded schema-version
prefix bumped — a legitimate update, not a workaround).

**Housekeeping:** `.env.local` (used for this) wasn't gitignored — added it
to `.gitignore`. It was also silently picked up by `pytest` (config.py
loads it unconditionally), which caused 32 spurious local test failures
until noticed and worked around; not a real regression, but worth flagging
in case anyone else hits the same confusion running local Supabase tests.

**Renumbered:** the previously-queued "migration 0006" (schema cleanup,
`workspace_id NOT NULL` / drop `owner_id`) is now migration **0009** —
0006–0008 were consumed by the fixes above.

The local Supabase stack (`apps/cloud/supabase/`, remapped to ports

## Update — security review caught a real privilege-escalation gap, fixed

Automated background security review flagged `pz_invitations_invitee_update`
(added in the previous update): RLS restricts rows, not columns — `email =
auth.email()` alone let any user who'd ever been invited to *any* workspace
rewrite that invitation's `workspace_id`/`role` to an arbitrary target and
self-escalate to admin there. Confirmed exploitable, fixed with a column-level
`GRANT update (status)` (app never touches other columns) plus a tightened
row policy (`pending` → `accepted`/`expired` only). Re-verified live: the
tamper attempt now fails on a permission error, the real accept flow still
works end-to-end, replay is a no-op. All 50 tests pass. Committed `cd14d86`.
Corrected `0008` in place rather than adding a `0009` patch — it was never
applied anywhere but a local throwaway test database.
