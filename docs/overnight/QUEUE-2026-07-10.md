## Update — implemented D1, found + resolved a D2 blocker

At the user's direct instruction ("implement, don't need to ask, it's
overnight-loop"), built and shipped D1 of `docs/plans/0004`: cloud
auth/login, per-project workspace linking, and a desktop UI panel. Verified
live end-to-end against real running `apps/cloud` + `apps/engine` instances
(login, workspace create/list, project create+link with the linked project
confirmed to exist cloud-side, unlink, logout, error paths) — not just
type-checked, actually exercised. All gates green throughout (ruff, 50/50
pytest, both `tsc --noEmit`). Committed as `b418cef`.

**Stopped before D2** on a real finding, not a judgment call to avoid work:
`apps/engine/src/db.ts`'s schema has no `updated_at` column on any table
(verified by reading the file, not assumed) — D2's plan text assumed one
existed for dirty-tracking. Documented the gap and a resolution in
`docs/plans/0004-desktop-cloud-sync-client.md` §D2 (recommend: D2's first
cut pushes a full snapshot per cycle instead of incremental deltas — local
project graphs are small enough that this is cheap, and it avoids a schema
migration touching every insert/update call site in `routes/projects.ts` /
`routes/agents.ts` before shipping any sync at all).

Chose not to push further into D2 in the same pass: the pull side needs to
translate cloud entity shape back into 5 local tables with joins the local
schema doesn't carry directly (`project_id` isn't on `spec_documents`/
`tasks`/`artifacts` locally, only reachable by walking the FK chain) and
none of it is exercised by any test — apps/engine has zero test
infrastructure today. Writing that untested, by curl-only verification,
risks a silent field-mapping bug that loses data on pull. That crosses from
"ship working code" into "ship code I can't actually vouch for," which is
worse than stopping at a clean, fully-verified D1 boundary.
