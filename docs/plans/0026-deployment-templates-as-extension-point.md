# Plan 0026 — Deployment templates as the extension point

**Date:** 2026-09-12 · **Status:** Exploratory — direction, with one concrete first template. That first step (FastAPI + Uvicorn python runtime) is open, carried into [plan 0029 §13](0029-agent-native-delivery.md#13-carried-over-open-work) · **ADR:** [0021](../decisions/0021-deployment-templates-seeded-ci-cloud-observed.md), [0023](../decisions/0023-development-preview-for-every-project-type.md), [0024](../decisions/0024-generated-deployment-scaffolds.md), [0025](../decisions/0025-provider-credentials-split-workspace-and-project.md), [0026](../decisions/0026-docker-compose-on-a-customer-host.md)

This plan answers [§4.2 bet four](../product-vision-2026-09-12.md) of the product vision: "adding one is a directory plus a registry entry, and the three-valued `credential_owner` already covers customer, platform and host ownership. This is the cheapest surface to grow and the one that widens which project types the platform can carry all the way to a live preview." The contract already makes a new template cheap; the question worth answering is which template comes next, and what the contract itself still lacks before a fifth one is built on top of it.

---

## 1. The contract as it stands

A `DeploymentTemplate` (`apps/cloud/app/deployments/registry.py:124-173`) is a dataclass: an id, a display-only `stack` string nothing dispatches on, a `provider`, a `scaffold_dir`, a `delivery_kind`, tuples of `SecretSpec`/`VarSpec`, an `embeddable` claim, a `health_path`, a `url_kind`, and a `platform_url_source`. `BUILTIN_TEMPLATES` (`:176-386`) holds four of these, and `get_template`/`template_files` (`:391-504`) are the only readers. By the module's docstring (`:40-50`), adding one is a directory plus a list entry plus, optionally, one `DeployProvider` entry — it must not touch `SeedFile`, the webhook contract, the `pz_deployments` row shape, `DeploymentConfig`/`DeploymentState`, or the lifecycle machine, and adds no inbound callback, cloud-side build step, route, or database column.

Three discriminators replace per-template branches. `delivery_kind` (`registry.py:76-87`) is "how the platform PRESENTS a build" — `embedded_url`, `external_url`, `api_console`, `artifact_download`, `store_build` — deliberately not `stack`. `url_kind` (`:153-156`) says whether the provider mints the URL (`next-vercel`) or the platform computes it (`static-r2`, `github-pages`, `docker-compose`). `platform_url_source` (`:157-169`) names how a platform URL is computed and is resolved in exactly one place, `apps/cloud/app/deployments/preview_url.py`, whose docstring (`:16-22`) explains why: before it existed, every non-`static-r2` platform-URL template was silently pinned against an R2 prefix it could never match, because both callers — `sync.create_repository`, needing it before the repo exists, and the webhook handler, validating a reported URL — called `platform_r2_preview_url` directly. `platform_preview_url` (`preview_url.py:65-110`) now branches on `platform_r2`, `project_value:<key>`, or `github_pages`, and both callers read it.

Credentials are declared by the template, supplied by the provider: `SecretSpec.from_provider` (`registry.py:91-104`) names the key a `DeployProvider` resolves; `VarSpec.source` (`:106-122`) is `project_id | template_id | environment | web_origin | preview_url | provider:<key> | literal:<value>`. `DeployProvider.credential_owner` (`deploy_providers.py:88-100`) is three-valued: `customer` (an admin connects a token — Vercel), `platform` (the cloud mints a per-workspace credential, only the minted one reaches a repo — `ensure_platform_r2_credential`, `deploy_providers.py:405-477`), `host` (the workflow's own ephemeral token — `github-pages`). ADR 0025's `CredentialField.scope` (`deploy_providers.py:64-79`) splits further: `workspace` fields sit on the account, `project` fields name the resource one project deploys to, living in `DeploymentConfig.provider_values` (`apps/cloud/app/models/schemas.py:394-405`), frozen at `repo_created`.

A composed scaffold is a directory convention: `is_composed_scaffold` (`registry.py:395-401`) checks for `base/`, and `template_files` (`:456-504`) seeds `base/` always, exactly one `runtimes/<name>/` variant, and `services/<name>.yaml` fragments spliced at the `# pz:services` marker. The variant is chosen by `plan_profile.derive_stack_profile` (`apps/cloud/app/deployments/plan_profile.py:75-97`), a word-bounded keyword count over the plan document. `_RUNTIME_KEYWORDS` (`:39-46`) knows `node`, `python` (via `fastapi`, `django`, `flask`, `uvicorn`, `pydantic`), and `go` (requiring a multi-word phrase like `golang`, so a plan saying "users go to the dashboard" cannot outscore it). `_SERVICE_KEYWORDS` (`:50-53`) knows `postgres` and `redis`. That vocabulary is the entire cost of a new composed variant.

ADR 0024 forbids one thing: a model may write files the workflow builds, never the files that deploy — the workflow, the Dockerfile, the secret contract, `docs/deployment.md` — because `create_repository` writes Actions secrets before it commits the scaffold, so a generated workflow would have credential access from its first run, driven by prompt-injectable plan text. `plan_profile.py` restates the same boundary (`:18-24`): it selects among hand-written files, never authors one, so its worst failure is a wrong placeholder the first implementation task overwrites. `template_files` sorts its output (`registry.py:415`, `:504`), so `(template_id, plan)` deterministically produces the same tree — what keeps a seeded pipeline reviewable.

## 2. What the four templates cover, and what they do not

Four ship, in registry order: `static-r2` (`platform-r2`, owner `platform`, `registry.py:178-216`), `github-pages` (`github-pages`, owner `host`, `:217-269`), `next-vercel` (`vercel`, owner `customer`, `:270-317`), `docker-compose` (`ssh-docker`, owner `customer`, `:322-385`). All three credential postures are exercised; `docker-compose` is the only composed scaffold.

Coverage is narrow: a static site (twice), a Next.js app, and a containerised service in one of three runtimes with an optional Postgres or Redis sidecar. `plan_profile.py`'s keyword tables recognise exactly three languages and two services; a Rails, Spring, .NET, or mobile plan scores zero and falls back to `DEFAULT_PROFILE` (`node`, `plan_profile.py:65`) — a wrong guess, not a failure. More structurally, every template is `delivery_kind="embedded_url"` (§3), so nothing targets a mobile build, an installer, or a plain API surface — those discriminators have no template behind them.

## 3. Where the contract is still thin

**`DELIVERY_KINDS` has four unexercised members.** `DELIVERY_KINDS` (`registry.py:85-87`) declares five values; `delivery_kind` defaults to `embedded_url` (`:145`). All four templates use it explicitly or by default — `github-pages` (`:233`), `next-vercel` (`:282`), `docker-compose` (`:336`), and `static-r2`, which relies on the default, confirmed by `test_static_r2_still_presents_as_an_embedded_url` (`apps/cloud/tests/test_deployment_templates.py:213-215`). `test_every_builtin_declares_a_known_delivery_kind` (`:208-210`) checks enum membership, not coverage. `external_url`, `api_console`, `artifact_download`, `store_build` are a discriminator with no implementation — `DeploymentTemplateOut.delivery_kind` (`apps/cloud/app/api/deployments.py:73`) can carry them, but nothing has ever produced one, so any rendering path for them is untested by construction.

**The `ws:<uuid>` namespace is designed-for and unbuilt.** `registry.py`'s docstring (`:33-38`) states future workspace-owned templates resolve as `ws:<uuid>` against a `pz_workspace_deployment_templates` table that does not exist. `test_every_builtin_id_is_a_bare_slug` (`test_deployment_templates.py:46-52`) enforces only the built-in half. `list_deployment_templates(workspace_id: str | None = None, ...)` (`apps/cloud/app/api/deployments.py:186-193`) accepts but, per its own comment, ignores the parameter; `test_list_endpoint_accepts_the_future_workspace_id_param` (`test_deployment_templates.py:193-197`) checks legality, not effect. `get_template` (`registry.py:391-392`) reads only `_BY_ID`, built from `BUILTIN_TEMPLATES`. No code resolves a colon-bearing id anywhere in `apps/cloud/app/deployments/` or `apps/cloud/app/api/deployments.py` — the scheme is a naming convention, not a resolver.

## 4. The recommendation: a FastAPI + PostgreSQL runtime variant on `docker-compose`

The vision's §4.1 names the buyer: Thai and Southeast Asian regulated organisations, drawn here because source never leaves their Git host and a deployment can run on a server they administer. `docker-compose` is already built for that buyer — ADR 0026 chose a customer-owned server over Cloud Run or Railway specifically because only that host makes Compose "load-bearing rather than decorative," and names a customer VPS as "the one users ask for."

The narrowest, highest-value gap is inside that template's own vocabulary, not a new one. `_RUNTIME_KEYWORDS` already recognises `fastapi` (`plan_profile.py:41`), and `apps/cloud/app/deployments/templates/docker-compose/runtimes/` already has `go`, `node`, and `python` variant directories, alongside a `postgres` fragment at `apps/cloud/app/deployments/templates/docker-compose/services/postgres.yaml`. The recommendation is not a new `DeploymentTemplate` or `DeployProvider` at all: it is auditing and, where thin, completing `apps/cloud/app/deployments/templates/docker-compose/runtimes/python/` as an explicit FastAPI + Uvicorn scaffold whose health route matches `health_path="/healthz"` (`registry.py:365`), and confirming its environment variables agree with the `postgres` fragment's. A regulated buyer's backend of choice in this market is overwhelmingly a Python API over Postgres — the pair this composed scaffold already has the pieces for but has not asserted as tested.

Nothing else changes: the provider stays `ssh-docker` (`deploy_providers.py:297-336`), owner `customer`; secrets and variables stay exactly what `docker-compose` already declares (`registry.py:337-359`); the preview URL still resolves via `url_kind="platform"`, `platform_url_source="project_value:public_url"` (`registry.py:368-369`), read by `preview_url.platform_preview_url`'s `project_value` branch (`preview_url.py:89-95`) out of `DeploymentConfig.provider_values`, because ADR 0026 has no API that can discover where a customer's box answers. `plan_profile.py`'s weighting is unchanged — a plan already scoring `fastapi` or `postgres` already selects this path.

The case against a genuinely new template first — a managed host, per ADR 0026's own open question — is the case ADR 0026 already made against `fly-node`: a managed single-container host does not make Compose load-bearing, and adds a fourth credential posture for a segment this vision does not prioritize.

## 5. Direction — what "extension point" would have to mean

Today a template is a directory in this repository, committed by whoever has write access here. Shipping a template is shipping the product: no discovery, no upload path, and per §3, no resolver for the `ws:<uuid>` ids that would let a workspace register its own. "Extension point" currently means cheap for this team to add to, not cheap for a customer or partner to.

Widening it runs into where ADR 0024 already drew its line. A customer-supplied template is, by definition, a workflow this codebase did not write, seeded the moment Actions secrets exist — the exact shape ADR 0024 refuses a model, now from a less trusted source. Every property §1 relies on — pinned action SHAs, no inline secrets, no `pull_request_target`, no path escape (tests cited in §6) — is enforced today by this repository's own review, not by anything that travels with an uploaded template. Making that safe means a submission-time linter with the same teeth run against untrusted input, plus a review queue and the `pz_workspace_deployment_templates` table the registry already anticipates.

That is buildable, and not worth building yet: four templates is too little signal to know what customers would submit, and the review burden of arbitrary CI from workspace admins is a cost worth paying once demand names it. The extension point should stay internal — cheap to widen, not yet safe to hand to anyone else.

## 6. Tests a new template must pass

`apps/cloud/tests/test_deployment_templates.py` sets the bar, and a new template — the `python`/`postgres` pair included — should extend it rather than invent a parallel one. Structural: a file at its declared `workflow_path` (`test_every_template_ships_a_scaffold_and_a_workflow`, `:60-64`), a bare unique id (`test_every_builtin_id_is_a_bare_slug`, `:46-52`; `test_ids_are_unique`, `:55-57`), and a `provider` that resolves (`test_every_declared_provider_exists`, `:67-69`). Declared-versus-used: every secret and variable name actually appears in the scaffold (`test_every_declared_secret_is_actually_read_by_the_workflow`, `:72-87`). Supply-chain: every `uses:` pins a 40-character SHA (`test_workflows_pin_every_action_to_a_full_sha`, `:90-99`), no line outside an `env:` mapping references `secrets.` (`test_workflows_never_interpolate_a_secret_inline`, `:102-114`), and no line contains `pull_request_target` (`test_pull_request_jobs_have_no_secret_access`, `:117-124`). Contract: `deployments: write` and `PZ_ENVIRONMENT` are present, and `PREVIEW_ENVIRONMENT` stays `"preview"` (`test_workflows_declare_the_preview_environment`, `:127-132`). File safety: no path escapes the template root or keeps a `.tmpl` suffix (`test_template_files_never_escape_the_template_directory`, `:135-141`; `test_tmpl_suffix_is_stripped`, `:144-150`). And `delivery_kind` must be a known member (`test_every_builtin_declares_a_known_delivery_kind`, `:208-210`) — necessary but not sufficient per §3, since membership does not prove the web app renders it. The first template to use one of the four untested `delivery_kind` values should add its own web-side rendering test, because nothing today proves that path works.
