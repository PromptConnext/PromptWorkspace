PromptWorkspace/Product reframing/Plan 0029

Agents do the work.
People govern the outcome.

Today we run a traditional delivery workflow with AI-written documents and made it faster. This proposes PromptWorkspace redesigned around autonomous agents, where people own intent, guardrails, decisions and trust.

Intent→ Scope→ Guardrails→ Agent planning→ Parallel execution→ Automated verification→ Human decisions→ Release
Date 2026-10-04 Status Draft for review Basis develop @ 444540e, ADRs 0001–0028 Full text docs/plans/0029-agent-native-delivery.md
01/The argument

The bottleneck moved. Our product didn't.

AI helps us at two points today: writing the plan documents, and inside each developer's private editor. Everything between those points is still built around people: assigning, claiming, copying context, dragging cards, verifying by eye.

Once implementation is cheap and parallel, the scarce resources are the four things only people can supply:

01

Intent

What outcome do we want, and how will we know we got it?

02

Guardrails

What must never happen, what must always hold, and who grants exceptions?

03

Decisions

What do we do when the spec is ambiguous or the risk is real?

04

Trust

Is this change proven well enough to ship?

The product should be organised around these four things, not around tasks.

08/Product model

Eight concepts the product is built on

Intent

Versioned "what and why", owned by the business owner.

Outcome

User-facing result O2 with plain-language acceptance scenarios O2.S1…

Guardrail

Rule with a level (prompt / check / gate), a scope and an owner.

Change

One PR-sized slice of one outcome: steps, areas, risk tier, budget, state.

Agent role

Instructions, tools, allowed paths, runtime, budget. Versioned in the repo.

Evidence Pack

CI, scenario proof, review findings, guardrail results, diff profile, run trace.

Decision

Typed request for human judgement: options, recommendation, evidence, who, why.

Release Candidate

Merged Changes on a build, readiness report, release decision.

09/Governance

Human approval by risk, not by task

Routine

Docs, tests only, copy, styling, no new dependency

Auto-merge when evidence complete
T1
Standard

Feature code inside approved outcomes and areas, Trust ≥ 80

Auto-merge; steward reviews in batch at release
T2
Elevated

New dependency, schema migration, public API change, Trust < 80

Steward approves this Change from its evidence
T3
Critical

Auth, payments, personal data (PDPA/GDPR), infra, secrets

Production release, whatever the tiers.

10/How the platform handles the hard parts

Conflicts, uncertainty, memory, rules

Conflicting changes: four layers, cheapest first
  • Avoid: plan predicts touched areas; running Changes hold area leases
  • Detect: builders rebase before PR and every retry
  • Catch: merge queue runs full CI on the combined result
  • Escalate: a Conflict decision with both diffs and options
When an agent is uncertain
  • Ambiguous spec, guardrail would break, unplanned dependency, repeated failures, budget exceeded
  • raise_question(options, recommendation, blocking) becomes a Decision routed to the business owner or steward
  • Only that Change pauses; non-blocking questions continue on the recommended option and flag the assumption in the PR
Shared memory: two layers
  • Authoritative: outcomes, constitution, ADRs, decisions log, baseline. People own it; agents may draft
  • Journal: per-run notes, searchable, never injected as rules
  • Promotion journal → rule only via an ADR proposal decision. Agents can't write their own rules
Rules with teeth
PromptInjected into every brief
CheckLint/test/scanner in verify.yml
GateRaises tier or blocks merge (e.g. agents may not edit .github/workflows/**, ADR 0024)

15/MVP

One delegated Change, end to end, on today's platform

M1 · Changes from tasks.md

The tasks template already has dependency-ordered phases (Setup → Foundational → one per user story → Polish). One Change per phase, no extra LLM call. Delivery Plan view + Plan approved.

M2 · Decisions

pw_decisions, Decision Inbox, project hats, email. Lifecycle routes gain the server-side checks that are client-only today.

M3 · Runner

Hand-written agent.yml seeded at provisioning. Claude Code headless with the customer's key. MCP get_change / raise_question / report_progress. Bounded retries.

M4 · Verification + evidence

verify.yml per template, scenario-tagged tests, one read-only Reviewer agent, Evidence Pack, Trust Score v1.

M5 · Risk gate

Risk policy v1 (path globs, deps, migrations, policy scope). promptworkspace/gate status. Branch protection seeded.

M6 · Mission Control

Outcome progress from scenario evidence, "needs you" strip, Release Candidate report on the Preview tab.

Done when (greenfield Next.js project)
  • 3+ user stories become Changes automatically
  • 2+ Changes run in parallel in Actions and open PRs with no human code
  • Every PR has an Evidence Pack with per-scenario proof
  • T0/T1 merges with zero clicks; T2 is blocked by branch protection until approved
  • An agent question reaches the right person and the answer resumes the run
Not in the MVP
  • Separate Security / Architecture / Docs agents (scanners + Reviewer checklist first)
  • Automatic semantic conflict resolution (serialise and escalate)
  • More than one runtime; per-PR previews; L2 autonomy
  • Staging/production split: MVP uses today's single preview environment from main

17/Example

Clinic booking app under Thai PDPA, idea to production in four days

Khun Ploy (clinic ops manager, business owner) · Arun (tech steward) · Mint (engineer, part-time) · Autonomy L1 · next-vercel

Day 1 AM · Intent

Ploy: "Patients book online, get an SMS reminder, staff see today's schedule." Intent agent drafts O1 Book, O2 Remind, O3 Schedule, and asks two questions. The consent question flags PDPA, so scenario O2.S4 "no SMS without opt-in" is added. Ploy approves the intent.

Day 1 PM · Guardrails + plan

Arun keeps the default constitution and pins patient data to lib/patients/**; PDPA makes those changes T3. Planning agent proposes six Changes, with C2 (auth) and C4 (reminders) predicted T3. Arun approves the plan; the repo is provisioned.

Day 2 · Execution

C1 merges automatically (T0). C2's agent asks "encrypt phone numbers at rest?", Arun answers and files an ADR from the agent's draft. C2 is T3: Arun reviews line by line, Ploy approves the data summary. C3, C4, C5 then run in parallel.

Day 3 · Verification catches a real bug

Security review flags a log line writing patient phone numbers. The builder fixes it on retry 1. C3 and C5 are T1 with Trust 91 and 86: auto-merged. C4 (T3) is approved by Arun and Ploy.

Day 4 · Release

Mission Control: O1 4/4 · O2 4/4 · O3 2/3 proven. Ploy tries the preview; "staff need to cancel bookings" becomes new intent O4. Arun and Ploy release without O3.S3; the gap is recorded in the decision.

18/More examples

A small brownfield feature, and a conflict between agents

Brownfield: CSV export on an imported Django repo
  • Business owner asks for shipment history export. Intent agent drafts 1 outcome, 3 scenarios incl. "only my own shipments"
  • Planner reads the baseline, finds exports/, plans one Change (C14, T1). One-click plan approval
  • Reviewer agent spots a missing tenant filter; the scenario test fails; builder fixes on retry 1
  • Trust 92, T1: merges with no human action. Owner gets "O7 proven on staging; try it"

Human time: ~5 minutes. Traditional: ticket, grooming, assignment, a developer day, review round-trip, manual QA.

Conflict: annual plans (C21) vs proration (C22)
  • Avoid: both touch billing/**; the lease runs C21 first, C22 waits
  • Detect: C22 rebases on merged C21 and passes its own tests
  • Catch: merge queue runs the full suite; a C21 annual-plan test fails
  • Decide: two retries fail and the scenarios truly conflict. Conflict decision goes to the business owner: prorate by day or by month? Picks "by day"; intent v3; both outcomes stay proven

A one-minute business decision, not a code-review surprise a week later.

19/What we need from the team

Four ADRs and five open questions

ADR 0029

The Change is the unit of delivery

One PR-sized outcome slice; tasks become steps; assignment and Kanban leave the main path.

ADR 0030

Agents execute in the customer's CI

Cloud orchestrates and observes; never runs code or holds coding-model keys.

ADR 0031

Risk-tiered, evidence-based gates

Approval by tier via a required status check; release always human.

ADR 0032

Decisions are first-class

Every judgement typed, routed, recorded; only a Decision promotes agent drafts to rules.

  1. Naming. "Change" (maps 1:1 to a PR) or Delivery / Slice / Mission?

  2. GitHub App vs PAT. The runner needs Actions, statuses and administration permissions, which strengthens the case for the App ADR 0017 deferred. Decide before M3.

  3. First runtime. Claude Code headless (adapter knowledge exists) or Codex CLI. One for the MVP.

  4. Business-user desktop (ADR 0028). Fold into Phase 4 here, served by Decision cards and notifications?

  5. Default autonomy for existing projects. L0, or no change until a steward opts in?
