# Plan 0017 — Make webhook secret handling recoverable

**Date:** 2026-09-12 · **Status:** Implemented 2026-09-20 · **ADR:** [0021](../decisions/0021-deployment-templates-seeded-ci-cloud-observed.md)

`apps/cloud/app/api/sync.py:313-352`, inside `create_repository`, registers each repository's inbound webhook and stores the signing secret it just generated. Every attempt — including a retry against a repository that already has a hook — mints a fresh secret with `new_webhook_secret()` (`apps/cloud/app/integrations/github.py:83-87`) and persists it. GitHub treats a duplicate-hook registration as a no-op: it keeps signing deliveries with whatever secret the *first* successful registration set, and the route's own event-repair path (`ensure_hook_events`, `apps/cloud/app/integrations/github.py:308-330`) documents in its own docstring that it deliberately leaves that remote secret untouched. The result is a retry that stores a secret GitHub is not using, silently and permanently. This plan closes that gap: reuse the persisted secret on a safe retry, stop mistaking an unrelated rejection for a completed registration, and give a genuine rotation a recoverable order of operations.

## The exact sequence that breaks it

`create_repository`'s webhook step runs only when `public_api_url` is configured (`apps/cloud/app/api/sync.py:313-314`). It generates a secret (`apps/cloud/app/api/sync.py:316`, `secret = new_webhook_secret()`), calls `create_repo_webhook` with it (`apps/cloud/app/api/sync.py:318`), and — unconditionally, whether that call created a new hook or found one already there — writes the generated secret into `pz_repo_webhooks` via `service_repo.upsert_repo_webhook(RepoWebhook(...))` (`apps/cloud/app/api/sync.py:336-341`). That write is a real replacement, not a merge: `InMemoryRepository.upsert_repo_webhook` overwrites the dict entry outright (`apps/cloud/app/db/repository.py:576-578`), and `SupabaseRepository.upsert_repo_webhook` does the same via `on_conflict="repo_full_name"` (`apps/cloud/app/db/supabase_repository.py:170-174`).

The duplicate is swallowed one layer down. `HttpGithubClient.create_repo_webhook` (`apps/cloud/app/integrations/github.py:471-499`) posts the new secret to `POST /repos/{repo}/hooks` and, on a 422 response, simply returns (`apps/cloud/app/integrations/github.py:493-494`) — its own comment calls this "a hook with this config already exists," not an error worth failing repo creation over. GitHub does not rotate the existing hook's secret on that 422; the previously-registered hook, with its previously-registered secret, is untouched. `ensure_hook_events`, called right after on line 324 to widen the hook's events on every attempt, confirms this from the other direction: its docstring states that re-running `create_repo_webhook` "swallows GitHub's 422 … as success … and makes re-registration a silent no-op" (`apps/cloud/app/integrations/github.py:311-317`), and it only ever calls `update_repo_hook` to change `events` (`apps/cloud/app/integrations/github.py:328`) — never `config.secret`. Nothing on this path reads GitHub's response to learn whether the sent secret was actually accepted.

So a retry against an already-hooked repository generates secret S2, POSTs it, receives 422, keeps going as if S2 is live, and stores S2 as `secret_ref` — while GitHub is still signing with S1. The consequence lands at the verification site: `github_webhook` looks up the binding by `repo_full_name` (`apps/cloud/app/api/github.py:170`), decrypts `binding.secret_ref` (`apps/cloud/app/api/github.py:177`), and calls `verify_signature(raw, signature, secret)` (`apps/cloud/app/api/github.py:183`) against S2. Every delivery — signed with S1 — fails, and the route returns `401 invalid_signature` (`apps/cloud/app/api/github.py:184`) before the payload is even parsed for routing.

## Why this is worse than it looks

A `401` here is not surfaced anywhere a human is watching. `_handle_deployment_status` (`apps/cloud/app/api/github.py:292-330`), which turns a `deployment_status` delivery into a `Deployment` row via `repo.upsert_deployment` and then calls `_refresh_deployment_state`, never runs — rejection happens before `github_webhook` branches on `event_type`. `refresh_deployment_state` (`apps/cloud/app/deployments/state.py:27-49`) reads `repo.list_deployments(project.id, limit=10)` and returns immediately when empty (`apps/cloud/app/deployments/state.py:36-37`); with no delivery ever verified, that list stays exactly as it was before the secret drifted. `Project.deployment_state.state`, rendered by `get_deployment_status` (`apps/cloud/app/api/deployments.py:337`, `state=state.state if state else "not_configured"`), therefore freezes at whatever it last was — `"awaiting_first_deploy"` if the drift happened on the first retry, per the placeholder `create_repository` writes at step 8. `last_error` in that same response (`apps/cloud/app/api/deployments.py:322-325,347-355`) comes only from rows with a `failed` state and `error_code`, and a 401 never reaches `repo.upsert_deployment` to create one. A stalled project therefore does not look broken: it looks like it is still waiting for its first deploy, indefinitely, with no error banner. It looks quiet.

## What already exists

`repair_webhook` (`apps/cloud/app/api/deployments.py:357-406`), at `POST /projects/{project_id}/deployment/repair-webhook`, is explicit about its scope: it is "the only migration path for repositories created before ADR 0021," whose hooks "carry `push` and `pull_request` only." It resolves the token, derives `full_name` from `project.repo_url`, and calls `ensure_hook_events` (`apps/cloud/app/api/deployments.py:391-401`) — the same function above that widens events and explicitly does not touch the secret. It fixes an under-subscribed hook; it cannot fix a drifted signing secret, since it never calls `create_repo_webhook` with a new secret and never writes to `pz_repo_webhooks`. This plan does not replace `repair_webhook` — it solves an adjacent, correctly-scoped problem — but M3 extends it, since it already carries every precondition a rotation needs: admin gating, token resolution, and `full_name`. A second endpoint re-deriving all three would be new machinery duplicating working machinery for no reason.

## M1 — Reuse the persisted secret on a retry

Before minting a new secret, check whether one is already bound to this repository. If a `RepoWebhook` exists for `full_name`, decrypt and reuse its plaintext instead of generating a new one, so a retry that lands on an already-hooked repository resends the *same* secret GitHub already accepted — a 422 or a 200 both leave the stored binding correct either way.

```python
service_repo = request.app.state.repository
existing_binding = service_repo.get_repo_webhook(full_name)
secret = (
    request.app.state.secret_store.decrypt(existing_binding.secret_ref)
    if existing_binding is not None
    else new_webhook_secret()
)
```

`create_repo_webhook(token, full_name, callback_url, secret)` and the subsequent `upsert_repo_webhook` call are otherwise unchanged — the upsert becomes a no-op write of the same value when `existing_binding` was reused, and still creates the first binding when it was `None`. This is the entire fix for the overwhelmingly common case: the same route, the same repository, no remote change intended.

## M2 — Distinguish a known duplicate from any other rejection

`create_repo_webhook`'s blanket `if resp.status_code == 422: return` (`apps/cloud/app/integrations/github.py:493-494`) treats every 422 as "a hook with this config already exists," but GitHub returns 422 for other validation failures too — a malformed `config.url`, an unsupported event after a future `WEBHOOK_EVENTS` change, a `content_type` the repository rejects. Swallowing all of those identically means an unrelated failure is mistaken for a completed registration exactly as easily as a real duplicate is. Narrow the check to the response body GitHub sends for the duplicate case specifically — `errors[].resource == "Hook"` with a message naming the existing config — and raise `GithubWriteError` for every other 422, the same exception the surrounding `except GithubWriteError` handling in `create_repository` already expects. With M1 in place this branch fires rarely, since a matching secret is resent and usually accepted outright; M2's value is that a *non*-duplicate 422 stops being silently treated as success.

## M3 — A deliberate rotation path

When the remote secret genuinely must change — a suspected leak, a compliance rotation policy — GitHub and the local binding have to be updated together in an order that cannot leave them disagreeing. Extend `repair_webhook` (`apps/cloud/app/api/deployments.py:357-406`) with a `rotate_secret: bool` body flag rather than adding a parallel endpoint, since it already resolves the token and `full_name` under admin gating. When set, the route: (1) generates the new secret locally but does not persist it yet; (2) calls `create_repo_webhook` (not `update_repo_hook`, which only ever takes `events`) with the new secret — GitHub's hook-update accepts a `config.secret` on the existing hook, so this updates the live hook's secret in place rather than creating a second one; (3) only after that call returns without raising, calls `service_repo.upsert_repo_webhook` with the new `secret_ref`.

GitHub first, local binding second, is the order and the reason is precise: if step 2 fails, the stored `secret_ref` still matches what GitHub is signing with, and the endpoint can simply be retried. The reverse order — store first, register second — reproduces the exact bug this plan exists to fix: a window where the local secret has changed but GitHub has not yet accepted it, during which every delivery fails verification the instant the local write lands, before any confirmation that GitHub agrees.

## M4 — A fake that models the real behaviour

`FakeGithubClient.create_repo_webhook` (`apps/cloud/app/integrations/github.py:1054-1066`) unconditionally appends a new entry to `self.webhooks` on every call — it never checks whether a hook for that `repo` already exists, so it cannot express GitHub's duplicate-detection behavior, and every test built on it today implicitly assumes each registration attempt is independent. The fake must instead track at most one hook per `repo` and, when `create_repo_webhook` is called a second time for a `repo` that already has one, keep the *first* call's `secret` rather than overwrite it — mirroring 422-then-unchanged-hook, not append-a-record. `list_repo_hooks` (`apps/cloud/app/integrations/github.py:1175-1180`) already reads `reversed(self.webhooks)` for a `repo`'s latest registered `url`; once `create_repo_webhook` stops appending duplicates, that lookup reflects the one hook GitHub would actually have.

With that fixed, two retry cases become testable that are not testable today: a retry against an already-hooked repo with M1 in place must find `fake.webhooks[0]["secret"]` unchanged after the second `create_repository` call, with the `secret_ref` from `service_repo.get_repo_webhook(full_name)` (asserted the way `test_create_repository_writes_the_webhook_binding_with_the_service_key` does today, `apps/cloud/tests/test_lifecycle.py:370-376`) decrypting to that same secret; and the same retry *without* M1 must show `binding.secret_ref` decrypting to a *different* value than `fake.webhooks[0]["secret"]` — turning the bug into a regression test. `test_create_repository_retry_adopts_existing_repo_without_duplicate_create` (`apps/cloud/tests/test_lifecycle.py:264-283`) exercises none of this today, because it never sets `public_api_url`, so the webhook block at `apps/cloud/app/api/sync.py:313-352` is skipped entirely; the new cases must set it explicitly, as `test_create_repository_writes_the_webhook_binding_with_the_service_key` (`apps/cloud/tests/test_lifecycle.py:346-376`) already does.

## Suggested commit sequence

1. `fix(cloud): reuse the persisted webhook secret on retry (M1)` — the reuse check in `create_repository`.
2. `fix(cloud): narrow create_repo_webhook's 422 handling to a known duplicate (M2)` — the body-shape check.
3. `feat(cloud): rotate a repo's webhook secret through repair-webhook (M3)` — the `rotate_secret` flag, GitHub-then-local ordering.
4. `test(cloud): make FakeGithubClient model duplicate hook registration (M4)` — the fake fix plus the retry-secret regression tests.

M1 is the fix that matters most and should ship alone if nothing else lands this cycle — small, low-risk, and it removes the failure mode for the overwhelmingly common retry case. M2 hardens the same call and can follow immediately. M3 is additive and changes no existing behavior until an admin opts into rotation. M4 should land with M1, since M1 is the change that most needs a regression test to stay fixed.
