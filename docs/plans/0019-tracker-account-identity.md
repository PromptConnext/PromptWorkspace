# Plan 0019 — Scope tracker identity to the provider account

**Date:** 2026-09-12 · **Status:** Ready for implementation · **ADR:** [0010](../decisions/0010-sync-model.md)

This plan closes finding 16 of `docs/cloud-codebase-review-2026-09-06.md` (High): an external tracker reference is treated as globally unique per *provider*, when a Jira issue key is only unique within a *site*. Findings 14 and 15 live in the same subsystem — `apps/cloud/app/api/integrations.py` and `apps/cloud/app/integrations/` — and are folded in as adjacent milestones so the account-identity model introduced for 16 is the one place ClickUp's credential gap and mirror idempotency get fixed too, rather than three separate patches touching the same files out of sequence.

---

## The identity gap

Inbound routing in `apps/cloud/app/api/integrations.py` never resolves *which* tracker installation sent a delivery — only which provider. `tracker_webhook` (`apps/cloud/app/api/integrations.py:167`) reads the provider from the URL path, fetches a single provider-wide secret via `_webhook_secret` (`apps/cloud/app/api/integrations.py:40-41`, backed by `settings.jira_webhook_secret` at `apps/cloud/app/config.py:68`), and verifies the raw body against it with `adapter.verify_signature` (`apps/cloud/app/integrations/jira.py:130-136`). Once verified, the payload is parsed into `InboundUpdate` records and each is routed with:

```python
link = repo.find_task_link_by_key(provider, update.external_key)
```

at `apps/cloud/app/api/integrations.py:197`. `find_task_link_by_key` (`apps/cloud/app/db/repository.py:323`, implemented in-memory at `apps/cloud/app/db/repository.py:1006-1007` and against Supabase at `apps/cloud/app/db/supabase_repository.py:772-781`) takes `(provider, external_key)` as its entire key and returns the first — in Supabase's case the only, per a `.limit(1)` — matching row. The comment path takes the identical shortcut: `_apply_inbound_comment` (`apps/cloud/app/api/integrations.py:218`) calls the same `find_task_link_by_key(provider, comment.external_key)` at line 219, and the deterministic discussion id it writes is built as

```python
id=f"{provider}-comment-{comment.comment_id}"
```

(`apps/cloud/app/api/integrations.py:229`) — provider and Jira's own comment id, nothing else.

The underlying table matches this shape exactly. `pz_task_links` in `apps/cloud/migrations/0005_tracker_links.sql:11-18` has `primary key (provider, external_key)`; the `TaskLink` model (`apps/cloud/app/models/schemas.py:322-330`) carries no site or account field to narrow that key with. `provider` distinguishes Jira from ClickUp; it says nothing about *which* Jira. Jira issue keys are short and sequential per project (`PZ-42`, `ENG-7`) and site administrators routinely reuse the same project key across independently provisioned Cloud sites. Two workspaces that each configure a Jira site under `integration_config["jira"]` (`apps/cloud/app/models/schemas.py:259`, `JiraIntegrationConfig` at line 333) and each happen to run a project keyed `PZ` will produce identical `external_key` values the moment both have a `PZ-1`. Whichever workspace mirrored first "owns" that row in `pz_task_links`; a delivery from either site's `PZ-1` updates that same task, permanently, regardless of which site actually sent it. The same holds for comments: two sites' issue `PZ-1` each posting a comment with Jira-internal id `10001` writes to `jira-comment-10001` in both cases, so the second delivery silently overwrites the first workspace's discussion row via the `upsert_graph` in `_apply_inbound_comment` (`apps/cloud/app/api/integrations.py:236-238`).

`apps/cloud/tests/test_sync.py:42` (`test_owner_isolation`) is the project-isolation test the codebase actually has, and it establishes something adjacent but different: that user *bob* cannot read or list a project owned by *alice* through the authenticated API. It says nothing about two *trackers* independently addressing the same `pz_task_links` row through an unauthenticated, signature-only webhook — that path has no per-caller identity to isolate on in the first place, which is exactly the gap this plan closes. No test in the suite constructs two Jira sites with colliding issue keys and asserts they cannot cross-update; finding 16's "existing project isolation tests do not establish safety" is accurate as written.

## A global webhook secret is not a routing credential

`_webhook_secret` returns one process-wide value for every Jira delivery, whoever sent it. A shared secret answers only "does the caller hold the secret configured for this provider" — it cannot answer "which account sent this," because by construction every account configured against the same deployment holds the same secret. Signature verification and routing are two different jobs: verification proves the delivery is not forged; routing decides which project it belongs to. Today the second job is done by trusting whatever `external_key` the payload claims, with no check that the account which currently owns that key is the account the secret was issued to. A delivery from a rogue or misconfigured second Jira site that happens to reuse a project key does not need to forge anything — the shared secret it was itself configured with already verifies, and the collision does the rest.

The repository has already solved this exact shape for GitHub, and this plan's job is to apply that pattern to trackers rather than invent a new one. Before ADR 0017's amendment, GitHub webhooks used a single platform-wide signing secret and workspace-scanning routing — the same class of first-match bug (issue #3, referenced in `apps/cloud/migrations/0020_repo_webhooks.sql:9-13`). The fix, in `apps/cloud/migrations/0020_repo_webhooks.sql`, was a `pz_repo_webhooks` table keyed by `repo_full_name text primary key` (line 17), holding a per-repository `secret_ref` (line 20) generated fresh at repo creation (`new_webhook_secret()`, `apps/cloud/app/integrations/github.py:83-87`) and stored as ciphertext through `apps/cloud/app/secrets.py`'s `FernetSecretStore` (class at line 38). `github_webhook` (`apps/cloud/app/api/github.py:154`) routes *before* it verifies: it looks up the binding by `repo_full_name` first (`apps/cloud/app/api/github.py:170`, `repo.get_repo_webhook`), decrypts that binding's own secret (line 176), and only then checks the signature against it (line 183) — the comment at lines 166-169 spells out why: "under per-repo secrets the repository *is* what selects the key." An unrecognized repository is dropped before its payload is trusted at all; a recognized one is verified against a secret that only that repository's registration could have produced. `RepoWebhook` (`apps/cloud/app/models/schemas.py:624-642`) is deliberately its own row rather than a field on `Project`, specifically so the ciphertext can never leak through a route that serializes `Project` directly (lines 628-631) — the same reasoning should carry over to whatever row holds a tracker account's secret.

Tracker identity needs the same three pieces GitHub already has: an identity narrower than "the provider" to route on, a secret scoped to that identity rather than to the provider, and routing performed before trust is extended to the payload's own claims.

## M1 — Give an integration an account identity

Jira's natural account identity is the site itself: `JiraIntegrationConfig.base_url` (`apps/cloud/app/models/schemas.py:337`, e.g. `https://your-org.atlassian.net`) is already unique per Jira Cloud tenant, already collected at configuration time (`configure_integration`, `apps/cloud/app/api/integrations.py:78-92`, which requires `base_url` and validates its host against `JiraAdapter.allowed_host_suffixes` at `apps/cloud/app/integrations/jira.py:35`), and is exactly the value that distinguishes two otherwise-identical Jira sites. An installation identifier would be more precise for providers that expose one, but Jira Cloud webhooks carry no stable installation id in their payload for this codebase to route on — `JiraAdapter.handle_webhook` (`apps/cloud/app/integrations/jira.py:81`) and `parse_comment_webhook` (line 111) read only `issue.key`, `fields`, and `comment` — so `base_url` is both the identity Jira actually exposes and the one already in hand. This plan uses the site base URL, normalized (scheme + host, trailing slash stripped) so `https://acme.atlassian.net` and `https://acme.atlassian.net/` are the same account.

New migration `0028_tracker_account_identity.sql` in `apps/cloud/migrations/`, numbered after the current high-water mark (`0027_deployment_tasks.sql`, confirmed by listing that directory):

- Add `pz_workspace_integrations`, one row per configured `(workspace_id, provider)` pair, replacing the provider-keyed JSON blob inside `integration_config` as the place that carries identity and secret: `workspace_id`, `provider`, `account_key text not null` (the normalized site base URL for Jira), and `webhook_secret_ref text not null` (ciphertext, same `secrets.py` treatment as `pz_repo_webhooks.secret_ref`). Unique on `(provider, account_key)` — this is the constraint that makes the collision this plan closes structurally impossible rather than merely unlikely: two workspaces cannot both register `jira` against the same `account_key`, so two sites can only coexist under this schema if their base URLs actually differ, which is the one thing operators cannot get wrong the way they can get a short issue-key prefix wrong.
- Add `account_key text not null default ''` to `pz_task_links` (additive, matching `0004_field_ownership.sql`'s style) so a link row records which account it belongs to.
- Drop the existing `primary key (provider, external_key)` on `pz_task_links` and replace it with `primary key (provider, account_key, external_key)`.
- RLS on `pz_workspace_integrations` mirrors `pz_task_links`' existing policy in `0005_tracker_links.sql:27-30` (`pz_is_member(workspace_id)`), since unlike `pz_repo_webhooks` this table's non-secret columns (`provider`, `account_key`) are useful to a member's own settings UI — only `webhook_secret_ref` needs the same "never reaches a browser session" treatment `0021_repo_webhooks_anon_revoke.sql` gave the GitHub table, so this migration also revokes `webhook_secret_ref` from `authenticated` via a restricted view or column-level grant, matching that precedent rather than inventing a new one.

`configure_integration` (`apps/cloud/app/api/integrations.py:78-92`) changes to compute `account_key` from the validated `base_url`, generate a fresh secret with a tracker analogue of `new_webhook_secret()`, encrypt it through `request.app.state.secret_store`, and upsert the `pz_workspace_integrations` row instead of only merging into `integration_config`. The existing `integration_config[provider]` blob keeps holding `base_url`/`project_key`/`status_map` — only the secret and account key move to the new table, mirroring how `RepoWebhook` stays a separate row from `Project` rather than replacing it.

## M2 — Bind each inbound delivery to a verified account

`tracker_webhook` (`apps/cloud/app/api/integrations.py:167`) changes its verification order to match `github_webhook`'s route-before-verify shape. Jira's webhook payload carries the site's own base URL in `self`/`issue.self` (a field Jira always populates and `JiraAdapter.handle_webhook` currently ignores), so the handler extracts and normalizes that host, looks up `pz_workspace_integrations` by `(provider, account_key)` to find the matching secret, decrypts it, and *then* calls `adapter.verify_signature` against that account-specific secret rather than the process-wide `settings.jira_webhook_secret`. A payload whose host matches no configured account is dropped before its signature is even checked, exactly as `github_webhook` drops an unrecognized `repo_full_name` at line 170-173 before touching the payload further.

Once verified, `account_key` travels with the request the rest of the way:

- `find_task_link_by_key` gains the parameter: `find_task_link_by_key(provider, account_key, external_key)`, implemented against the new three-column primary key in both `apps/cloud/app/db/repository.py:1006-1007` (in-memory) and `apps/cloud/app/db/supabase_repository.py:772-781` (adds `.eq("account_key", account_key)` alongside the existing `.eq("provider", ...)`/`.eq("external_key", ...)` filters).
- `mirror_task` (`apps/cloud/app/api/integrations.py:98`) stamps `account_key` onto every `TaskLink` it writes, sourced from the workspace's own `pz_workspace_integrations` row rather than from anything the caller supplies — an authenticated member mirroring a task cannot claim a different account's identity, only the one their workspace is actually configured against.
- The deterministic comment id in `_apply_inbound_comment` (`apps/cloud/app/api/integrations.py:229`) becomes `f"{provider}-{account_key}-comment-{comment.comment_id}"`, so two sites' `10001` can no longer collide on the same discussion row.

The `(provider, account_key, external_key)` primary key from M1 is what turns this from "very unlikely to collide" into "cannot collide": a second site attempting to mirror what it believes is the same `external_key` under its own `account_key` gets its own row, full stop, and an inbound delivery that fails to resolve an `account_key` at all — because its host matches no configured `pz_workspace_integrations` row — never reaches `find_task_link_by_key`.

## M3 — Make mirroring idempotent

Finding 15: `mirror_task` (`apps/cloud/app/api/integrations.py:98-145`) never reads `pz_task_links` before calling `adapter.build_push` and creating a new external issue; `repo.upsert_task_link(link)` at line 145 then replaces whatever link previously existed for that task, orphaning the issue that link pointed to. A retried click, a client double-submit, or a network-timeout retry with the create having actually succeeded server-side all produce a duplicate Jira issue plus a lost linkage to the first one.

In scope for this plan: before building the outbound request, `mirror_task` calls `repo.get_task_link(task_id, provider)` (already implemented at `apps/cloud/app/db/repository.py:1000-1001` and `apps/cloud/app/db/supabase_repository.py:760-770`, just currently unused by this route). If a link exists, the route returns it unchanged instead of calling the adapter at all — the "at minimum" option the review names as in-scope even without update support. Full update-in-place (calling Jira's edit-issue endpoint when a link already exists) is explicitly out of scope for this plan: it needs a `build_update` builder per adapter beyond the `build_push`/`build_transition` pair `JiraAdapter` has today (`apps/cloud/app/integrations/jira.py:39-51, 68-76`), and mixing that in here would blur M1/M2's identity fix with a second, independently reviewable change to outbound behavior. Returning the existing link removes the duplicate-issue and orphaned-linkage failure mode described in the finding; a follow-on plan can add true synchronization once this one has shipped.

## M4 — Resolve ClickUp honestly

Finding 14: `ClickUpAdapter` is registered in `apps/cloud/app/integrations/registry.py:9-12` alongside Jira, and `configure_integration` (`apps/cloud/app/api/integrations.py:78`) accepts a `clickup` config with no special-casing. But `_outbound_auth` (`apps/cloud/app/api/integrations.py:62-67`) only branches on `provider == "jira"` and falls through to `None` for anything else, so `mirror_task` always raises `tracker_credentials_missing` (line 129) for ClickUp; `_webhook_secret` (line 40-41) is a literal `{"jira": ...}` dict, so `_SIGNATURE_HEADER["clickup"]` at line 37 picks a header that is then checked against an empty string, and `ClickUpAdapter.verify_signature` (`apps/cloud/app/integrations/clickup.py:63-66`) returns `False` for a missing secret exactly as designed — inbound ClickUp verification cannot ever pass.

Recommendation: mark ClickUp unavailable in the registry rather than complete its credential path in this plan. `list_providers()` (`apps/cloud/app/integrations/registry.py:15-16`) and `get_adapter()` (lines 13-14) change to distinguish adapters that are merely *registered* (both entries in `_ADAPTERS`) from those that are *available* — a second dict or a `credentials_configured: bool` attribute the settings/`providers` endpoint (`apps/cloud/app/api/integrations.py:247-249`) filters on before advertising a provider through `GET /integrations/providers`, and `configure_integration` rejects configuring an unavailable provider with a clear `provider_unavailable` detail rather than silently accepting settings nothing can use. This is the smaller, honest fix: completing ClickUp's credential path means designing a second provider's settings surface (its own `_outbound_auth` case, its own per-account secret analogous to what M1 builds for Jira, its own settings UI affordance) that has no first user driving it, while today's actual defect is a catalog that promises working ClickUp support it cannot deliver. The reasoning in the review's own recommendation — "keep provider capabilities and credential resolution together" — is the same reasoning M1 already applies to Jira's new `pz_workspace_integrations` row: a provider only appears configurable where its credential and account-identity path actually exists end to end. Once a real second provider is built, it goes through that same table rather than through a Jira-specific one, and the availability flag flips naturally.

## M5 — Tests

New `test_tracker_account_identity.py` in `apps/cloud/tests/`, matching the fixture and `client` shape used by `apps/cloud/tests/test_sync.py` and `apps/cloud/tests/test_jira_comments.py` (both already exercise this router against `InMemoryRepository`):

1. **Two sites, identical issue keys, no cross-project update.** Configure two workspaces' `jira` integration with different `base_url`s (e.g. `https://site-a.atlassian.net`, `https://site-b.atlassian.net`) but the same `project_key`. Mirror a task in each so both end up with `external_key == "PZ-1"` but distinct `account_key`s. Send an inbound `jira:issue_updated` webhook whose payload's `issue.self` matches site A and whose `issue.key` is `PZ-1`, signed with site A's secret. Assert only site A's task changed and site B's task is untouched. Repeat with a webhook signed under site B's secret targeting `PZ-1` and assert the reverse. Also assert a webhook whose payload host resolves to no configured `account_key` at all is rejected (401) before any link lookup runs.
2. **Identical comment identifiers, no cross-project mirroring.** Same two-site setup; deliver a `comment_created` webhook for `PZ-1` with the identical Jira-internal `comment.id` under each site's own secret and assert two separate `Discussion` rows are created — one per project — rather than the second overwriting the first (guards the `id=f"{provider}-{account_key}-comment-{comment.comment_id}"` construction from M2).
3. **Repeated mirror, no duplicate issue.** Call `mirror_task` for a task, then call it again for the same task without an intervening unlink; assert the second call returns the identical `TaskLink` (same `external_key`) and that no second outbound create request was attempted — a fake/counting adapter transport, following the pattern `apps/cloud/tests/test_jira_comments.py` already uses for a stubbed adapter, makes the "no second call" half of this assertion checkable directly.

Run: `cd apps/cloud && pytest tests/test_tracker_account_identity.py -v && ruff check .` (the test module path here is a run command, not a repository citation, since the file does not exist until this plan is implemented).

## Suggested commit sequence

1. `feat(cloud): add per-account tracker identity (M1)` — migration 0028, `pz_workspace_integrations`, `configure_integration` account-key + secret generation.
2. `feat(cloud): bind inbound tracker webhooks to a verified account (M2)` — route-before-verify in `tracker_webhook`, `account_key`-scoped `find_task_link_by_key`, scoped comment ids.
3. `fix(cloud): return the existing link on a repeated mirror (M3)`.
4. `fix(cloud): mark ClickUp unavailable until its credential path exists (M4)`.
5. `test(cloud): two-site collision and repeat-mirror coverage (M5)`.

M1+M2 are the load-bearing security fix and should land together; M3 and M4 are independent of each other and of M1/M2's schema change, so either can be sequenced first if there is reason to ship one sooner.
