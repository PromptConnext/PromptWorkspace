# Plan 0015 — Constrain full-graph writes to an authorized surface

**Date:** 2026-09-12 · **Status:** Ready for implementation · **ADR:** [0020](../decisions/0020-cloud-is-the-source-of-truth.md)

This plan closes finding 1 of the [cloud codebase review](../cloud-codebase-review-2026-09-06.md): the cloud now claims authority over the task graph, but it kept the old write surface without enforcing the new boundary. `push_graph` (`apps/cloud/app/api/sync.py:616-653`) checks project membership only and accepts the caller's declared authority domain, while the dedicated single-field routes — `assign_task` (`apps/cloud/app/api/sync.py:532-562`) and `set_task_status` (`apps/cloud/app/api/sync.py:565-613`) — forbid a member from setting `verified` or touching another person's task, and stage authoring restricts plan and constitution writes to admins. The weaker door is still open next to the stronger one. Plan [0012-close-the-write-path.md](0012-close-the-write-path.md) owns the *direction* of sync — it stops the engine from being a caller of `push_graph` at all. This plan owns the *permission model* on whatever survives that route, per 0012's own "Out of scope" note (`docs/plans/0012-close-the-write-path.md:91`).

## The four concrete bypasses

**A review status the status route forbids.** `set_task_status` refuses a non-admin who sets `TaskStatus.verified` (`apps/cloud/app/api/sync.py:599-600`, `403 verified_requires_admin`). `push_graph` (`apps/cloud/app/api/sync.py:617-625`) calls `require_project` — membership only — then `repo.upsert_graph(project_id, payload, source=payload.source)` with no role check at all. `status` is `"pz"` authority in `FIELD_AUTHORITY["tasks"]` (`apps/cloud/app/models/schemas.py:531-539`), so any project member pushing `source: "pz"` with a task carrying `status: "verified"` writes the same field the dedicated route just refused them.

**A reassignment the assignment route forbids.** `assign_task` restricts a non-admin to self-assign or self-unassign (`apps/cloud/app/api/sync.py:548-554`, `403 assignment_forbidden`). `assigned_user_id` is also `"pz"` authority (`apps/cloud/app/models/schemas.py:538`), so the same unauthenticated-for-role `push_graph` path lets any member reassign anyone's task, including a task not their own.

**A plan or constitution write `require_stage_access` gates.** `ADMIN_ONLY_STAGES = frozenset({"constitution", "plan"})` (`apps/cloud/app/api/_guards.py:39`) and `require_stage_access` (`apps/cloud/app/api/_guards.py:42-45`) block a non-admin from authoring those two stages through the generation and stage-document routes. Neither guard is imported by `sync.py`. A member pushing a `SpecDocument` through `push_graph` writes `content` directly (`"pz"` authority, `apps/cloud/app/models/schemas.py:541`) with no stage check at all — admin-only plan authoring is bypassed entirely by going through graph sync instead of the stage-document API.

**Acceptance criteria cleared through a model default.** `Task.acceptance_criteria` is `list[AcceptanceCriterion] = Field(default_factory=list)` (`apps/cloud/app/models/schemas.py:156`) and is `"pz"` authority (`apps/cloud/app/models/schemas.py:534`). The unset-field filter that protects against exactly this problem is `_OMIT_IF_UNSET` in `apps/cloud/app/db/merge.py:37`, and it holds exactly one field: `frozenset({"assigned_user_id"})`. `acceptance_criteria` is not in it. `incoming_dump` (`apps/cloud/app/db/merge.py:40-49`) calls `item.model_dump(mode="json")` unconditionally and only strips the fields named in `_OMIT_IF_UNSET`, so a pushed `Task` that never mentions `acceptance_criteria` still serializes it as `[]`. Because the pusher's `source` is `"pz"` and the field's authority is `"pz"`, `merge_entity`'s domain gate (`apps/cloud/app/db/merge.py:100-109`) admits the write, and LWW admits it too unless a newer field version is already stamped. The result: any `source: "pz"` graph push that constructs a `Task` without explicitly copying its acceptance criteria — trivially easy, since the field defaults silently — clears them. This is confirmed by reading the code, not assumed: `assigned_user_id` was deliberately special-cased for precisely this failure mode (`apps/cloud/app/db/merge.py:31-37`), and `acceptance_criteria` was not, despite sharing the same shape (a `pz`-owned collection with no independent "unset" representation in a full model dump).

## Client-declared authority

`GraphUpsertRequest.source` (`apps/cloud/app/models/schemas.py:564`) is `Literal["pz", "pmo"] = "pz"`, and `push_graph` passes it straight through: `source=payload.source` (`apps/cloud/app/api/sync.py:625`). No other caller in the codebase does this. Every internal call to `repo.upsert_graph` passes a literal, hardcoded domain: `generation.py:502,513,531` and `projection.py:93,115` always pass `source="pz"`; `github.py:531` and `discussions.py:55` do the same; the inbound tracker webhook, `tracker_webhook` (`apps/cloud/app/api/integrations.py:166-167`), verifies the provider's signature before doing anything and then calls `repo.upsert_graph(..., source="pmo")` with a hardcoded string (`apps/cloud/app/api/integrations.py:211-212`) — the domain is never read from the request body. `push_graph` is the only route where the writer picks its own authority domain. A member who sets `source: "pmo"` in the request JSON writes `assignee`, `sprint`, and `feature_tag` — otherwise tracker-exclusive fields (`apps/cloud/app/models/schemas.py:535-537`) — with no tracker credential at all; a member who sets `source: "pz"` gets every bypass above.

The field-authority machinery in `merge.py` was built to arbitrate a *local author against a tracker mirror*: an AI-native `pz` write and a Jira/ClickUp `pmo` write landing on the same row, each honest about which fields it owns (`apps/cloud/app/db/merge.py:1-21`). That boundary genuinely has two writers on opposite ends of a signed webhook and a project-membership check, and it should keep both. What it was never built for is letting one side of that boundary announce which side it's on.

## M1 — Decide the endpoint's fate

Two options. **Retire the route** once no client calls it — clean, but premature today. **Keep it as a constrained compatibility endpoint** for a bounded period — recommended now. Plan 0012's M1 deletes the *automatic* push from the engine's sync interval (`apps/engine/src/sync/loop.ts:498`) but deliberately leaves `pushProjectSnapshot` reachable from the manual route (`apps/engine/src/routes/cloud.ts:417-418`) until its own M4 deletes `assembleSnapshot`/`pushProjectSnapshot` outright and replaces them with a status-write queue. Until that M4 ships, `PUT /sync/projects/{id}/graph` still has one real caller. Retirement is safe once 0012's M4 lands and no route in `apps/engine` or `apps/vscode` calls it — confirm by grep for `PUT.*sync/projects` call sites outside tests before deleting `push_graph`. Note that retiring the HTTP route does not touch the tracker webhook path: `tracker_webhook` calls `repo.upsert_graph` directly, in-process, never through this router.

## M2 — Derive the writer domain from the authenticated path

Stop trusting `payload.source`. `push_graph` is only ever called by an engine acting as the local author, so its writer domain is `"pz"` unconditionally — the same way `discussions.py:55`, `github.py:531`, `generation.py:502` already hardcode it:

```python
# apps/cloud/app/api/sync.py
counts, conflicts = repo.upsert_graph(project_id, payload, source="pz")
```

Drop `source` from `GraphUpsertRequest` entirely, or keep the field for backward JSON compatibility and ignore its value — the second is safer during the compatibility window M1 chose, since an old engine binary that still sends `source` in the body must not get a 422 on an otherwise-valid push.

## M3 — Enforce the same rules at every door

Import `require_stage_access`, `Role`, and the ownership checks `assign_task`/`set_task_status` already have, and apply them inside `push_graph` before calling `upsert_graph`: reject a `SpecDocument` write when the caller isn't an admin and the document's stage is in `ADMIN_ONLY_STAGES` (mirroring `apps/cloud/app/api/_guards.py:42-45`); reject a `Task` whose `status` is `verified` from a non-admin; reject a `Task` whose `assigned_user_id` changes to anyone but the caller from a non-admin. Put this as one function — `_check_graph_write_permissions(repo, project, caller_role, payload)` — in `_guards.py` next to `require_stage_access`, not inline in `sync.py`, so a fourth route built against the graph tomorrow imports the same gate instead of re-deriving it. While here, close the related first-write gap finding 17 names: `merge_entity`'s no-stored-row branch (`apps/cloud/app/db/merge.py:90-94`) accepts an incoming entity wholesale, bypassing the domain gate for every field on first insert, not just the ones the writer owns. A `push_graph` call that fabricates a *new* task id can therefore author `status`/`acceptance_criteria` on creation even after M2 fixes the domain, since the row has no prior version to gate against. Route creation of new pz-authoritative entities through the same permission check as an update, not just the merge engine's steady-state path.

## M4 — Cross-endpoint authorization regression tests

The review's specific recommendation (finding 1's last sentence). For each rule a dedicated route enforces, assert `push_graph` refuses it too, in the same file that already exercises that rule: add cases to `apps/cloud/tests/test_task_status.py` asserting a member's `push_graph` carrying `status: "verified"` on someone else's task is rejected the same way `set_task_status` rejects it; add cases to `apps/cloud/tests/test_task_assignment.py` asserting a member's `push_graph` reassigning a task to a third party is rejected; add cases to `apps/cloud/tests/test_stage_access.py` (which already covers `admin_required` for plan/constitution authoring, e.g. `apps/cloud/tests/test_stage_access.py:64-70`) asserting the equivalent `push_graph` spec-document write is rejected for the same stages; add a case to `apps/cloud/tests/test_merge.py` asserting a `source: "pmo"` value in the request body no longer changes which fields a `push_graph` call can touch. Every case should assert the identical `detail` string the dedicated route returns, so a future divergence between the two doors shows up as a literal string mismatch, not a passing-but-differently-worded test.

## Suggested commit sequence

1. `test(cloud): pin the four push_graph bypasses as failing regression cases (M4, red)` — written first, expected to fail, proves the bug before fixing it.
2. `fix(cloud): derive push_graph's writer domain from the authenticated path (M2)`.
3. `fix(cloud): enforce stage, status and assignment rules on push_graph; close the first-write gate (M3)` — the M4 cases from commit 1 now pass.
4. `docs(cloud): record push_graph as a bounded compatibility endpoint pending 0012 M4 (M1)`.
