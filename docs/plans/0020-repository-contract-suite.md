# Plan 0020 — A repository contract suite that runs against both adapters

**Date:** 2026-09-12 · **Status:** Implemented 2026-09-22 (M1-M5; `apps/cloud/tests/contract/`, verified against a real local Supabase target — findings 4 and 17's second half reproduce deterministically, recorded `xfail(strict=True)` pending their fixes). **Finding 4 has no owning plan** — flagged for a follow-up plan, not fixed here (out of this plan's scope by its own M3 boundary).

[Finding 22](../cloud-codebase-review-2026-09-06.md) of the cloud codebase review is the specification this plan implements, and it is the one finding that explains the others. The review's validation run produced **558 passed, 1 failed** against `apps/cloud`, and three separately-reported High and Medium defects — findings 3, 4 and 17 — sat inside that green run untouched. They were not missed because the suite is thin. They were missed because all 558 tests exercised `InMemoryRepository` and none exercised `SupabaseRepository`, the class that actually runs in production. A passing cloud test today establishes the behaviour of the in-memory double; it establishes nothing about the adapter behind `DATA_BACKEND=supabase`.

This plan is the root-cause fix underneath `0013-graph-pagination-contract.md`, `0014-row-level-security-parity.md` and every other adapter-level repair the review recommends. It should be sequenced early — not because it is the most urgent defect, but because after it lands each of those fixes becomes verifiable, and before it lands none of them are.

## What the fixture guarantees today

`apps/cloud/tests/conftest.py` runs before `app.config` is imported and pins the environment by hand. Line 15 is the whole of it:

```python
os.environ["DATA_BACKEND"] = "memory"
```

The surrounding comment (`apps/cloud/tests/conftest.py:11-14`) is explicit about why: real process environment variables take precedence over `env_file` values in pydantic-settings, so a developer who exported `DATA_BACKEND=supabase` in their shell would otherwise drag a live database into the unit suite. The same block pins `AUTH_MODE=stub` (`apps/cloud/tests/conftest.py:16`) and drops the three `SUPABASE_*` variables. The `client` fixture (`apps/cloud/tests/conftest.py:44-49`) then builds a fresh app per test, and `_build_repository` (`apps/cloud/app/main.py:66-75`) reads `settings.data_backend` and returns `InMemoryRepository()` on line 75 without ever importing `app.db.supabase_repository`.

This is a good default and the plan does not weaken it. It is what makes `pytest -q` runnable offline, with no container, and fast enough that people actually run it. The defect is not the default but the absence of any second mode: `DATA_BACKEND` is a module-level assignment in a file pytest imports exactly once, so no test, marker or flag can ask for the other adapter. The suite does not merely default to memory — it is structurally incapable of running anything else.

## The divergences this would have caught

**Graph pagination (finding 3).** `InMemoryRepository.get_graph` (`apps/cloud/app/db/repository.py:836`) gathers candidates from every entity type into one list, sorts globally by `(updated_at, id)`, and applies a single `limit` to the merged result. `SupabaseRepository.get_graph` (`apps/cloud/app/db/supabase_repository.py:557`) issues one query per entity type, applies `limit` to each independently, filters the keyset continuation in Python *after* the database has truncated, and never sets `has_more` or `next_id`. The abstract declaration both implement (`apps/cloud/app/db/repository.py:245-256`) says only that `limit` plus `(after_ts, after_id)` "give keyset pagination ordered by (updated_at, id)" — which both can honestly claim to do, differently. `0013-graph-pagination-contract.md` owns this one and supplies its own cases; this plan does not duplicate them.

**Assigned-task filtering applied after the limit (finding 4).** `InMemoryRepository.list_assigned_tasks` (`apps/cloud/app/db/repository.py:737`) skips projects outside the requested workspace, re-checks membership per project, sorts deterministically (`apps/cloud/app/db/repository.py:772`) and only then slices: `return out[:limit]` (`apps/cloud/app/db/repository.py:773`). `SupabaseRepository.list_assigned_tasks` (`apps/cloud/app/db/supabase_repository.py:415`) resolves the caller's workspace set first but then queries tasks filtered only on `assigned_user_id` and `deleted_at` and truncates immediately — `rows = (q.limit(limit).execute().data) or []` (`apps/cloud/app/db/supabase_repository.py:440`). The workspace restriction lands afterwards, in Python, at `if p["workspace_id"] in ws_ids` (`apps/cloud/app/db/supabase_repository.py:449`), and the sort after that (`apps/cloud/app/db/supabase_repository.py:476`). A user with 200 assigned tasks across three workspaces can ask for one and be handed an empty list. `apps/cloud/tests/test_my_tasks.py` covers both halves separately — `test_workspace_filter` at line 131, `test_limit_caps_results` at line 170 — and passes, because in memory the two never interact.

**The merge gate's read-modify-write (finding 17).** `merge_entity` (`apps/cloud/app/db/merge.py:65`) takes a first write wholesale — `if not stored:` at line 90 accepts every incoming field regardless of the writer's ownership domain — while an update runs the full gate (`apps/cloud/app/db/merge.py:100-108`). `SupabaseRepository.upsert_graph` performs that merge outside any transaction: `_fetch_row` on line 537, `merge_entity` on line 539, `upsert` on line 544, with no version predicate between them. `assign_task` (`apps/cloud/app/db/supabase_repository.py:640`) and `set_task_status` (`apps/cloud/app/db/supabase_repository.py:657`) repeat the shape on the `field_versions` map. `apps/cloud/tests/test_merge.py` tests `merge_entity` as a pure function — `test_concurrent_edits_to_different_fields_both_survive` at line 50 calls it twice in sequence — so the interleaving that loses a write is not expressible there at all.

## M1 — Separate the contract from the fixtures

Add a contract module that talks to a `Repository` through its public interface only and does not know which implementation it holds. `Repository` (`apps/cloud/app/db/repository.py:58`) declares 66 abstract methods; the contract covers only the invariants in M3. The home is a new package *apps/cloud/tests/contract/* with a `conftest.py` of its own, so the root fixture's pinning stays exactly as it is for every other test.

That local conftest exposes one fixture, `repo`, parametrised over the backends available in the environment. The memory parameter constructs `InMemoryRepository()` (`apps/cloud/app/db/repository.py:496`). The supabase parameter constructs `SupabaseRepository(url, key)` (`apps/cloud/app/db/supabase_repository.py:86`) from a dedicated pair of variables — `PZ_CONTRACT_SUPABASE_URL` / `PZ_CONTRACT_SUPABASE_KEY`, deliberately *not* `SUPABASE_URL`/`SUPABASE_KEY`, which the root conftest deletes — and is skipped with a reason naming the missing variable when they are absent. Never silently skip and report green. Register a `contract` marker beside the existing `eval` marker in `apps/cloud/pyproject.toml` (the `markers` list, lines 10-12) so the two backends are selectable and reportable independently. Neither adapter is built through `create_app`, so the FastAPI `client` fixture and `get_repository`'s per-request JWT scoping (`apps/cloud/app/dependencies.py:103-122`) are out of the picture — this suite tests the data layer, not the router. The default `pytest -q` must behave as it does today apart from the added memory-parametrised cases: same order-of-magnitude runtime, no new entry in `apps/cloud/requirements.txt`, no network.

## M2 — A disposable Supabase target

This is the expensive milestone and the plan should say so. The smallest real thing is the Supabase CLI's local stack, which this repository is already configured for: `supabase/config.toml` exists at the repo root, pins `project_id = "PromptZone"`, Postgres `major_version = 17`, and the database on port 54322. `supabase start` brings up a usable Postgres and PostgREST with no new configuration file.

Schema application should reuse `apps/cloud/scripts/migrate.py` rather than grow a second path. It already discovers the 27 files in `apps/cloud/migrations/` in numeric order (`apps/cloud/scripts/migrate.py:140`), resolves a connection string from `--db-url` then `$DATABASE_URL` then `$SUPABASE_DB_URL` (`apps/cloud/scripts/migrate.py:154`), and applies what is pending (`apps/cloud/scripts/migrate.py:469`). Two caveats. The ledger it maintains, `pz_schema_migrations` (`apps/cloud/scripts/migrate.py:74`, created by `apps/cloud/migrations/0024_schema_migrations_ledger.sql`), exists for incremental production use and buys nothing for a database that starts empty every run — harmless, not helpful. And `apps/cloud/migrations/0023_configurable_embed_dim.sql` refuses to apply without `--var embed_dim=<N>`, so the setup command is `scripts/migrate.py apply --var embed_dim=1024`.

Reset by teardown, not by `delete from`: `supabase db reset` re-creates from scratch, which is faster than truncating in dependency order and immune to a new migration being forgotten in a hand-written cleanup list. Credentials never enter the repository — the local stack's keys are printed by `supabase start` and read from the two `PZ_CONTRACT_*` variables; a hosted disposable project supplies the same two from CI secrets. This buys the ability to assert that production code satisfies the same invariants as the double. It costs a container runtime, about a minute of startup, and a second place migrations must succeed.

## M3 — The contract cases

Group cases by the invariant they protect, not by the method that exposes it — a method-shaped suite drifts into re-testing each adapter's implementation, which is how the current suite got here.

**Keyset pagination and continuation.** Owned by `0013-graph-pagination-contract.md`. This plan's contribution is the harness: once M1 exists, that plan's parametrised module should move under *apps/cloud/tests/contract/* and use the shared `repo` fixture rather than standing up its own. Do not restate its cases.

**Membership and visibility scoping.** `get_membership` and `list_members` (`apps/cloud/app/db/repository.py:583`, `:587`; `apps/cloud/app/db/supabase_repository.py:187`, `:199`) are the predicate every read above them depends on. Assert that a removed member immediately stops seeing a workspace's projects and tasks even where a stale `assigned_user_id` still names them — the guarantee the interface docstring makes at `apps/cloud/app/db/repository.py:150-155`. `0014-row-level-security-parity.md` addresses the same boundary one layer down in Postgres; its M4 needs two real JWTs and direct PostgREST calls, which M2's local stack makes possible, and it should build on that rather than a third harness.

**Filtering before limiting.** Finding 4 directly: one user with tasks in three workspaces, more than `limit` in total and fewer than `limit` in the workspace under test; request that workspace and assert the list is complete and deterministically ordered. Repeat with a status filter plus a limit. Both adapters must return the identical set in the identical order.

**Concurrent field-level merge.** Finding 17: two writers in different ownership domains updating disjoint fields of one entity, interleaved so both read before either writes; assert both survive with correct per-field versions. Add the first-write case — an entity created by a `pmo` writer carrying `pz`-owned fields — and assert those fields are dropped, not accepted, matching what an update already does. Against memory this is trivially satisfied; against Postgres it is the case that will fail first, which is the point.

**Tombstones and cursors.** `purge_expired_tombstones` (`apps/cloud/app/db/repository.py:1010`, `apps/cloud/app/db/supabase_repository.py:785`) and `changes_head` (`apps/cloud/app/db/repository.py:889`, `apps/cloud/app/db/supabase_repository.py:597`) together decide what a desktop client believes about deletions. Assert a soft-deleted entity is absent from a bootstrap pull and present in an incremental one, that `changes_head`'s cursor and per-type counts agree with a full `get_graph` for the same `since`, and that purging an expired tombstone never moves the cursor backwards.

## M4 — Make it run

`apps/cloud` has no continuous integration at all. `.github/workflows/` holds `desktop-build.yml`, `desktop-theia-build.yml` and `theia-spike-windows.yml`, none of which runs Python; `docs/DEPLOYMENT.md` §6 still describes a cloud job running `pytest` + `ruff` as a recommendation rather than a thing that exists. Standing that up is `0021-operational-floor.md`'s subject and this plan does not duplicate it.

The minimum required here: the memory-parametrised contract cases run on every change to `apps/cloud/**`, in the same job as the existing suite, because they cost nothing beyond the tests already there. The supabase-parametrised cases run nightly on a scheduled job that brings up the local stack, applies migrations per M2, and reports the skip-versus-run distinction explicitly — a nightly that skipped every supabase case must not read as green. Any change touching `apps/cloud/app/db/**` should additionally be able to trigger the supabase job on demand, since that is exactly the diff for which nightly turnaround is too slow.

## M5 — Two honest fixes to existing tests

**The DNS-dependent unit test.** `test_probe_accepts_an_ordinary_public_host` (`apps/cloud/tests/test_deployments.py:467`) asserts `_probe_target_is_public("https://example.com/index.html") is True`, and that helper (`apps/cloud/app/api/github.py:392`) resolves the hostname for real via `socket.getaddrinfo` (`apps/cloud/app/api/github.py:415`). It is the single failure in the review's run and passed on a rerun outside the sandbox — an environment artifact, but one that makes the suite lie about its own hermeticity. Monkeypatch `socket.getaddrinfo` to return a fixed public address tuple, which tests what the function is for — the all-addresses-must-be-public rule at `apps/cloud/app/api/github.py:396-398` — rather than testing IANA's DNS. Keep a real-resolver check if it is genuinely wanted, but behind a marker the default run excludes, as `eval` already is.

**The webhook fake that cannot fail.** `FakeGithubClient` (`apps/cloud/app/integrations/github.py:978`) implements `create_repo_webhook` (line 1054) by unconditionally appending to `self.webhooks` and calling `hooks_events.setdefault`. The real client (`apps/cloud/app/integrations/github.py:471`) instead receives a 422 when a hook with that config already exists and returns silently, treating it as success (`apps/cloud/app/integrations/github.py:491-494`). The fake models a second registration as "a new hook with the new secret," the opposite of what GitHub does — which is why the retry defect in `0017-webhook-secret-rotation.md` is invisible to `test_create_repository_retry_adopts_existing_repo_without_duplicate_create` (`apps/cloud/tests/test_lifecycle.py:264`). Make the fake refuse a duplicate: when a webhook already exists for the same `(repo, url)`, record the attempt in `call_log` and return without mutating the stored secret. Plan 0017 owns the production behaviour; this plan owns only the fake telling the truth.

## Verification

From `apps/cloud` with the venv active, three runs. `pytest -q` must show the pre-existing count plus the new memory-parametrised cases, all passing, with no network and no container — and, after M5, with no failure from the DNS test. `pytest -q -m contract` with `PZ_CONTRACT_SUPABASE_*` unset must skip every supabase-parametrised case with a reason naming the missing variable while the memory ones pass. With `supabase start` running and migrations applied per M2, that same command must execute both parameters, so each M3 case appears twice in the output with matching status. `ruff check .` must pass throughout. A reviewer should require evidence of the third run specifically: the first two prove the harness exists, only the third proves it reaches the adapter the review was worried about.
