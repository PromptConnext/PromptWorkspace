# Plan 0018 — Give stage regeneration a stable identity

**Date:** 2026-09-12 · **Status:** Ready for implementation · **ADR:** [0013](../decisions/0013-managed-thai-llm-tier-stage-routing.md), [0004](../decisions/0004-skill-owns-task-generation.md)

The cloud Planner (ADR 0013) gives a business user two ways to change a stage, and today they behave nothing alike. Clicking Generate runs the model and lands a fresh set of graph entities; editing the Raw markdown and saving updates the entities already there. For `specify` and `plan` the difference is mostly invisible, since both paths converge on the same single Requirement or SpecDocument row. For `tasks` it is not: every generation run mints a brand-new batch of `Task` rows, and nothing retires the batch it replaces. Regenerate a checklist twice and the tasks stage document says one thing while the Tasks board holds two overlapping generations — the older one still carrying whatever assignments, statuses, and commit artifacts accumulated on it. `apps/cloud/app/generation/projection.py:1-19` documents this as deliberate ("Editing the tasks markdown by hand therefore changes the document, not the board; regenerate to rebuild it"), but the review behind this plan (`docs/cloud-codebase-review-2026-09-06.md`, findings 5 and 6) is right that a deliberate gap is still a gap: the document and its projection carry no consistency state, so nothing tells the user they disagree. This plan closes the identity problem (finding 5) and the missing consistency signal (finding 6), and folds in finding 7's indexing inconsistency since it shares the same fix.

## What each path does today

The generated path lives in `apps/cloud/app/api/generation.py`. A successful `tasks` run calls `_persist_tasks(repo, project, spec, result)` at `apps/cloud/app/api/generation.py:284`. That function (`apps/cloud/app/api/generation.py:517-532`) parses the checklist with `parse_task_lines` and builds a plain list of `Task(...)` objects — no `id=` is ever passed, so each gets a fresh UUID from `Task`'s inherited default (`GraphEntity.id: str = Field(default_factory=new_id)` at `apps/cloud/app/models/schemas.py:120`, `new_id()` at `apps/cloud/app/models/schemas.py:23-24`). The batch goes to `repo.upsert_graph(project.id, GraphUpsertRequest(tasks=tasks), source="pz")`. Inside `InMemoryRepository.upsert_graph` (`apps/cloud/app/db/repository.py:809-834`), each item is merged by `stored = store[etype].get(item.id)` (line 822); since the id is new, `stored` is `None`, `merge_entity` treats it as an insert, and the row lands as an addition, not a replacement. Nothing looks at the tasks already there. `_persist_requirement` and `_persist_spec_document` (`apps/cloud/app/api/generation.py:495-516`) do the same thing structurally, but it doesn't show because there is normally one Requirement and one SpecDocument per project — regenerating `specify` or `plan` quietly orphans a prior row too; nothing reads the orphan.

The manual path is `apps/cloud/app/api/stage_documents.py:61-98` (`update_stage_document`). It saves the raw markdown via `repo.upsert_stage_document(...)`, then calls `project_stage_document(repo, project, stage, body.content)` (`apps/cloud/app/generation/projection.py:68-105`). For `specify` that function fetches `repo.get_latest_requirement(project.id)` and, if one exists, applies `existing.model_copy(update={"title": title})` — same id, same row, in place; `plan` does the same against `get_latest_spec_document`. The module's own `PROJECTION_NODE_TYPE` dict (`apps/cloud/app/generation/projection.py:39-42`) maps only `"specify"` and `"plan"` to graph node types — `tasks` is absent by design, and `project_stage_document` returns `None` for it (`apps/cloud/app/generation/projection.py:105-116`). So a Tech Lead who edits the tasks document by hand and saves gets a persisted document with no graph effect — the board simply does not move, silently, which is finding 6's complaint applied to the stage where it is most damaging: the checklist a person is looking at directly.

## The blast radius of a duplicate generation

Three consequences follow directly from tasks never being reconciled or retired.

First, commit attribution breaks. `colliding_refs` (`apps/cloud/app/integrations/task_refs.py:78-88`) exists precisely because two tasks can carry the same normalized reference, and `tasks_by_ref` (`apps/cloud/app/integrations/task_refs.py:110-125`) omits any ref with more than one match rather than guess which task a commit meant (line 122). Regenerating `tasks` reliably produces this: `_persist_tasks` assigns `feature_tag` from the parsed `T###` ref (`apps/cloud/app/api/generation.py:522-529`), so a second run mints new rows carrying the same `T1`, `T2`, ... tags as the first. `apps/cloud/app/api/github.py:581-593` calls `tasks_by_ref` on every push to attribute commits by subject; once a ref collides, `by_ref.get(ref)` returns nothing for it (line 591), so every commit naming that task, old generation or new, is silently un-attributed — worse than misattribution, since it raises no error to investigate.

Second, progress rollups count obsolete work. `apps/web/src/components/project/ProgressRollup.tsx:24-42` builds its denominator with `graph.tasks.filter((t) => t.spec_id && specIds.has(t.spec_id))` — every live task whose `spec_id` matches the current spec document, with no notion of "which generation." Since `_persist_tasks` always runs against the same `spec.id` (the latest SpecDocument, itself updated in place by `plan`), a second `tasks` run produces a second cohort under the identical `spec_id`, and both sum into one rollup, inflating numerator and denominator alike.

Third, assignments and statuses on retired tasks stay live. `Task.assigned_user_id`, `Task.status`, and their `field_versions` (`apps/cloud/app/models/schemas.py:150-163`) belong to the row, not to "the task with this title" — the old row is untouched by regeneration, so an assignee who claimed `T3` in the first generation keeps that claim and its status, and keeps any `Artifact` a push had attributed to it (`apps/cloud/app/models/schemas.py:165-170`), even though the checklist the team now sees no longer mentions `T3`.

Are references unique within a project today? No — `task_ref_from_feature_tag` derives a ref purely from `feature_tag` text (`apps/cloud/app/integrations/task_refs.py:52-56`), and neither `_persist_tasks` nor `upsert_graph` enforces uniqueness across rows; `colliding_refs` exists downstream specifically because the write path allows the collision.

## M1 — One application service for both paths

The review's central recommendation is structural: generated and edited content must go through the same code, or they keep drifting by construction. This belongs in `apps/cloud/app/generation/`, next to `projection.py` and `parsing.py` — a new `stage_apply.py` module exposing one function, `apply_stage_content(repo, project, stage, content, *, source, actor_id) -> StageApplyResult`, carrying the saved document id, the touched graph entity id(s), and a `projection: Literal["current", "pending", "failed", "not_applicable"]` field (feeding M4). `apps/cloud/app/api/generation.py`'s `_persist_requirement`/`_persist_spec_document`/`_persist_tasks` and `apps/cloud/app/api/stage_documents.py:76-94`'s call into `project_stage_document` both become callers; `project_stage_document`'s per-stage branches (`apps/cloud/app/generation/projection.py:81-104`) become its body, extended to cover `tasks` per M2/M3. The RAG enqueue calls duplicated at `apps/cloud/app/api/generation.py:264-267`, `apps/cloud/app/api/stage_documents.py:78`, and `apps/cloud/app/api/stage_documents.py:92-95` move inside the service too, answering finding 7: one write path decides what gets a fresh embedding, instead of three routes remembering independently. (`apps/cloud/app/api/sync.py`'s `push_graph`/`set_task_status` write through the graph-merge path finding 1 flags, and stay out of scope here.)

## M2 — Stable task identity within a project or an explicit plan revision

Pick stable identity **within a project**, not a plan-revision concept. A revision would require threading a `plan_revision_id` through `Task`, `SpecDocument`, `Artifact`, and every query that joins them (`ProgressRollup.tsx`, `tasks_by_ref`, the attribution consumers at `apps/cloud/app/api/github.py:503-504,581-593`) — a second axis of identity for a requirement that is really just "the same checklist item, regenerated, is the same task." Project-scoped stability satisfies that and reuses machinery the schema already has. `apply_stage_content`'s `tasks` branch keys incoming parsed rows by their normalized ref (`task_ref_from_feature_tag`, already used for attribution) against the project's current live tasks: a ref that already exists gets `existing.model_copy(update={"title": ..., "acceptance_criteria": ...})` — same id, same assignee, same status, same `field_versions`, only content moving — the update-in-place pattern `project_stage_document` already uses for `specify`/`plan` (`apps/cloud/app/generation/projection.py:87-90,100-103`). A ref with no existing match is a genuine insert — the smallest change making "regenerate twice" idempotent on identity without a revision model this codebase has no other use for.

## M3 — Define retirement

A ref present in the previous generation but absent from the new one is retired, not deleted. `GraphEntity` already has the tombstone this needs: `deleted_at` (`apps/cloud/app/models/schemas.py:114-118,122`), set by `apply_stage_content` as an ordinary field update — the same mechanism `purge_expired_tombstones` (`apps/cloud/app/db/repository.py:328-331`) already expects and excludes from bootstrap pulls, so a retired task disappears from the next fresh `GET .../graph` with no new endpoint. Retirement never touches `Artifact` rows: they key on `task_id`, not `Task.deleted_at` (`apps/cloud/app/models/schemas.py:165-170`), and `tasks_by_ref`'s `getattr(task, "deleted_at", None) is not None` guard (`apps/cloud/app/integrations/task_refs.py:122`) already excludes tombstoned tasks from *future* attribution — evidence already recorded is untouched history. `ProgressRollup.tsx:24` reads `graph.tasks`, which for a normal (`since=None`) fetch already omits tombstoned rows per `get_graph`'s own bootstrap-pull rule (`apps/cloud/app/db/repository.py:854-855`); once retirement sets `deleted_at`, a retired task stops counting toward progress with no change to the rollup itself. Stated plainly: a task a regeneration removes is tombstoned, not erased; its status, assignee, and every `Artifact` survive on that row for audit; it counts toward nothing going forward.

## M4 — An honest consistency state

`StageApplyResult.projection` (M1) is what both routes now report instead of implying success. `update_stage_document` currently returns only `StageDocumentOut` — the raw document, silent about the graph (`apps/cloud/app/api/stage_documents.py:63-71,90-97`) — and swallows a projection exception behind a log line the caller never sees (`apps/cloud/app/api/stage_documents.py:80-86`). That response gains a `projection: "current" | "pending" | "failed" | "not_applicable"` field, and the same field is added to `generation.py`'s stream `done` payload (`apps/cloud/app/api/generation.py:245-249`) so both paths speak one vocabulary. `tasks` is deliberately *not* made a draft-with-explicit-apply for manual edits — M2/M3 give it real projection now, so `apply_stage_content` runs it inline like `specify`/`plan`, reporting `"current"` on success or `"failed"` (document still saved) on the same partial-failure terms `stage_documents.py` already promises elsewhere. The Planner (`apps/web/src/components/project/Planner.tsx`) must show this: today a completed `tasks` generation renders only `${result.task_count} tasks created` (line 337-338), and a manual save shows `Last saved {time}` (line 362-365) with no board-state signal. Both should render `projection` — "current" needs no extra copy, "failed" should say the board didn't update and link to Tasks, matching the amber treatment `Planner.tsx:319-334` already uses for truncated generations.

## M5 — Tests

Add to `apps/cloud/tests/`, alongside the existing generation/projection suites: (1) regenerate `tasks` twice against the same checklist and assert `tasks_by_ref` on the resulting graph has no ref in `colliding_refs` — every `T###` maps to exactly one live task; (2) retire a task carrying an `Artifact` (via `upsert_task_artifact`) and a non-default status, then assert the `Artifact` and the task's `status`/`assigned_user_id` are unchanged on the tombstoned row, and `repo.get_graph(project_id)` (bootstrap, `since=None`) no longer includes it; (3) hand-edit the `tasks` document through `update_stage_document` with content that parses cleanly and assert the response's `projection` is `"current"` and the board reflects the edit; (4) the inverse — an unparseable checklist saved manually — and assert the document is still persisted, `projection` is `"failed"`, and the graph is untouched, per `apps/cloud/app/api/stage_documents.py:80-83`'s existing save guarantee.
