# Plan 0027 — Make an imported repository a first-class planning input

**Date:** 2026-09-22 · **Status:** Cloud implemented 2026-09-22 (M1–M5); the web client (M6) is pending. · **ADR:** [0017](../decisions/0017-cloud-creates-project-repo-at-tech-review-exit.md) (amended 2026-09-22), [0021](../decisions/0021-deployment-templates-seeded-ci-cloud-observed.md), [0024](../decisions/0024-generated-deployment-scaffolds.md), [0026](../decisions/0026-docker-compose-on-a-customer-host.md), [0027](../decisions/0027-what-is-free.md)

The choice between starting from scratch and importing an existing GitHub repository already exists. [Plan 0016](0016-repository-provisioning-identity.md) added it: `POST /projects` takes an `import_repo_full_name`, records `repo_url` at creation, and `create_repository` adopts that repository at tech-review exit instead of creating one. Both paths then run the same Planner — constitution, specify, plan, tasks, create repository — and end in the same place.

What that left out is that the platform never read the code it imported. Four gaps followed from that one omission. The stage generator in `apps/cloud/app/api/generation.py` built its context from the policy scope, the constitution and the uploaded PRDs only, so an imported project's plan and tasks were written as if nothing existed yet. The seed commit was built on the branch's base tree, so it silently overwrote any `README.md`, `AGENTS.md`, `docs/*`, `.specify/memory/constitution.md`, scaffold file or deploy workflow the team already had at those paths. The existing code was never indexed for the assistant — only files a later push touched ever were. And `derive_stack_profile` chose a composed scaffold's runtime from the plan text alone, ignoring the manifests sitting in the repository.

The decisions this plan was built on were confirmed before it was written: GitHub only, on the existing workspace PAT, webhook and deploy pipeline; a deterministic snapshot of the repository plus one model-written "codebase baseline" document, both fed into the stages; and a seed that never overwrites a file, with the platform's own documents under a folder it owns and a preview of the commit before it happens. The intended outcome is that both flows still end at `repo_created` with a plan and tasks, and for an imported repository those describe *changes to the existing codebase* while its files are left untouched.

---

## M1 — A deterministic snapshot

`apps/cloud/app/imports/snapshot.py` reads one commit of the repository without a model. It pins the default branch's head through a new `get_branch_head` on the GitHub client, lists the tree at that sha through a new `get_tree` (the recursive trees API, reporting GitHub's own `truncated` flag rather than raising on it), and filters the listing before anything else looks at it: vendored and build directories, binary files, and every secret-shaped file — `.env*`, private keys and certificates, `id_rsa*`, `.npmrc`, Terraform state, credential JSON — are dropped. That last filter is the security property the module is built around. A secret-shaped file is not summarised, not excerpted and not fetched, so it reaches neither the prompt nor the database row; a filter that only kept it out of the excerpts would still have leaked its name into a prompt and its content into a fetch.

What survives becomes a `RepoSnapshot`: the pinned `commit_sha`, a per-directory tree summary two levels deep, the stack detected from root-level manifests (with the most common source languages as a fallback), excerpts of a fixed list of files — the README, `AGENTS.md`, `CLAUDE.md`, an existing constitution, the manifests, Dockerfiles and compose files, and `.github/workflows/*` — capped at 8,000 characters per file and 30,000 in total, and the filtered paths capped at 2,000. The functions are pure over a path list, in the style of `repo_seed.py`, and the one async function only sequences reads through the injected client.

The result lives in a new table, `pz_repo_analyses` (migration `0034_repo_analyses.sql`), one row per project holding the current analysis: `commit_sha`, the `snapshot` as jsonb, the `baseline` text, a `status` of `snapshot_ready`, `baseline_ready` or `failed`, `created_by` and `updated_at`. It is not a stage document — `pz_stage_documents.stage` is a closed check on purpose, and the baseline is an input to planning rather than a Spec Kit stage. The table is born service-only: the migration revokes the grant `0006_grants.sql`'s default privileges would otherwise hand `authenticated`, and `pz_repo_analyses` joins `_SERVICE_ONLY_TABLES` in `supabase_repository.py`. Both adapters implement `get_repo_analysis` and `upsert_repo_analysis`; `tests/contract/test_repo_analyses.py` pins the jsonb round trip on both, and `tests/rls/test_graph_table_grants.py` gained a probe that a member's direct PostgREST write and read are refused with `42501`.

## M2 — The codebase baseline, and the API around it

A new router, `apps/cloud/app/api/repo_analysis.py`, carries three routes. `POST /projects/{id}/repo-analysis` is admin-only and refuses a project with no `repo_url` (`repo_not_imported`) or one already at `repo_created` (`repo_already_created`). It resolves the model and the daily token budget through the same `_resolve_model` stage generation uses, builds and stores the snapshot, then streams one baseline generation over SSE in the shape `POST .../generate/{stage}` already has: an `event: snapshot` as soon as the repository is read, `data: {"delta": ...}` lines while the model writes, and a final `event: done` or `event: error`. The run is recorded in `generation_runs` under the stage name `codebase_baseline` and charged to the workspace's ADR 0027 budget; the output is stored and never regenerated on its own, because every regeneration costs the same budget again.

The driver prompt is `codebase_baseline_prompt()` in `generation/prompts.py`, over a new template with the sections the plan named: purpose, stack, architecture and modules, conventions observed, test and CI setup, deployment signals, gaps and risks. Repository content is treated as untrusted prompt input. Everything read from the repository sits between `<untrusted_repository_content>` markers, the system prompt says what lies between them is data and that instructions found there are never followed, and any copy of a marker inside the repository's own text is neutralised so a README cannot close the block early.

`GET` returns the analysis to any member, answering `status: "none"` rather than 404 when there is none, the way an unsaved stage document answers with empty content. While the analysis still matters — an imported project before `repo_created` — it adds `stale`, from one branch-head read compared against the stored `commit_sha`. Push webhooks cannot answer that question, since the repository's hook is registered at `repo_created`, after the analysis has stopped mattering; a read that fails reports `null` rather than `false`, because "unknown" and "fresh" are different facts. `PATCH` lets an admin edit the baseline by hand, the same way a stage document is edited. A non-empty edit is `baseline_ready`, which also means a Tech Lead whose workspace is out of budget can open the gate by writing the baseline themselves; clearing it closes the gate again.

## M3 — Feeding the analysis into the stages

`generate()` now reads the project's analysis and, when it has a baseline, adds two labelled segments to the context: `[codebase_baseline]`, capped, and a compact `[repo_snapshot]` with the stack and the tree summary. The constitution gets the baseline capped at about 6,000 characters, so it adopts the conventions the code already follows. `specify` and `plan` take the baseline, capped at 12,000, out of the 40,000-character document budget after the policy summary and the constitution and before the PRDs, so the two do not compete for the same space. `tasks` gets it capped at 6,000, directly after the plan it breaks down, so tasks are phrased as changes to modules that exist. Both segments are labelled as reference material rather than instructions, since the baseline was written by a model reading untrusted text and an admin may have edited it since. `POST /prefill/{stage}` injects the same baseline for `specify` and `plan`, and reports it among its sources.

The gate is what makes the analysis a step rather than an option: for a project with `repo_url` set before `repo_created`, `plan` and `tasks` answer `409 repo_analysis_required` until a `baseline_ready` analysis exists. A snapshot without a baseline does not open it — injecting less than the gate asks for would let a stage run on half the context the gate promised. The check runs before the model is resolved, so a refused request costs no budget. The `plan` and `tasks` driver prompts gain one conditional line — plan changes against the codebase in `[codebase_baseline]`, reuse its modules and conventions, do not re-scaffold — and every other project's prompt is byte-identical to what it was.

`derive_stack_profile` takes an optional `detected_runtime`. When the snapshot's manifests name a runtime the composed scaffold can seed, it wins over the plan's keywords; services still come from the plan, and a runtime with no scaffold is ignored rather than trusted. `create_repository` and the seed preview pass the stored analysis's runtime through `build_deployment_files`.

## M4 — Seeding without overwriting

`fit_to_existing_repo` in `integrations/repo_seed.py` rewrites a seed so it never writes a path the repository already has, and returns a `SeedPlan` of the files to write together with what was relocated, skipped or in conflict. The derived views — `README.md` and the `docs/{scope,architecture,tasks,conventions,policy-scope}.md` set, plus the template's `docs/deployment.md` — always move under `docs/promptzone/`, whether or not their original paths are taken, so a platform file never squats on a conventional path the team may want later. `AGENTS.md` and `.specify/memory/constitution.md` are written where the tools look for them only when those paths are free, and otherwise go to `docs/promptzone/AGENTS.md` and `docs/promptzone/constitution.md`. Anything still colliding after that is dropped, including a `docs/promptzone/*` file a previous import left behind. Deployment scaffold files that already exist are skipped one by one — the team's own `Dockerfile` stays theirs — but a workflow file is a conflict, not a skip: silently skipping `.github/workflows/deploy.yml` would leave a project whose secrets, variables and preview state all say "deployable" with the team's unrelated workflow behind them, and merging into it is what ADR 0024 forbids. `create_repository` refuses with `409 deploy_workflow_conflict` before anything is written, and the Tech Lead either picks no template or moves the file first.

`create_repository` reads the live tree at the default branch's head right after adopting the imported repository and before any mutation, so the check cannot race a push the stored snapshot never saw. A repository this project created itself — the crash-window retry, where `repo_url` was recorded before the seed commit landed — is recognised by the description the platform writes at creation, the same provenance signal the name-collision retry already uses, and keeps the full, unrelocated seed it always had. A from-scratch project reads no tree at all and seeds byte-identically to before. An imported repository that already carries every file the seed would write gets no commit, since an empty seed is not an error. The fake GitHub client's `create_commit_with_files` now asserts that no path in the repository's pre-existing tree is written, which turns the no-overwrite guarantee into a test failure rather than a silently replaced blob.

`GET /projects/{id}/repository/seed-preview`, admin-only, runs the same builders and the same `fit_to_existing_repo` against the same live tree and returns `{write, relocated: [{from, to}], skipped, conflicts}`. The one difference is that it never resolves the deployment provider, which can mint a platform credential; the template's files are built without a preview URL, which changes one document's text and never a path.

## M5 — An initial code index

A repository created by the platform starts with a handful of seeded files and is indexed push by push. An imported one arrives with its history already written, and nothing would push most of it again. So at the `repo_created` flip, an imported project enqueues one `code_file` job per indexable path of the tree it just read, pinned to the pre-seed head sha — the same job the push webhook enqueues, so the worker path is shared — capped at 500 files and skipped outright when the workspace has no model connection, the condition under which the worker would drop every job anyway. The reindex panel reaches code too: `enqueue_project_backfill` adds one `code_tree` job per project at `repo_created`, which the worker expands into per-file jobs off the request path, since listing a tree is a GitHub call and the sweep runs on a request thread.

## M6 — The web client

Pending, in `apps/web`: a codebase analysis panel on the Planner's Foundation tab while an imported project is before `repo_created`, streaming `POST .../repo-analysis` and showing the stack, the tree summary, the baseline (editable by admins) and a stale badge; a "analyze the repository first" state on the Plan and Tasks tabs mapped from `repo_analysis_required`; and the seed preview in place of the static seeded-files list on the import consent step and in the create-repository panel.

## Verification

`cd apps/cloud && pytest && ruff check .` covers the cloud half. `tests/test_repo_snapshot.py` pins the filters, the secret exclusions, the caps and the truncated tree. `tests/test_repo_analysis_api.py` covers admin-only access, the refusal after `repo_created`, the stored snapshot and baseline, the budget charge and the recorded run, the delimiting of repository content, a failed baseline, the `PATCH` edit and the stale flag, then the stage side: the baseline segments present for an imported project and absent for a from-scratch one, and the `409` gate on `plan` and `tasks`. `tests/test_repo_import.py` shows an existing `README.md` and `AGENTS.md` surviving `create_repository`, derived documents landing under `docs/promptzone/`, `deploy_workflow_conflict` refusing with nothing written, the seed preview matching the actual commit, the from-scratch seed unchanged, and the initial code index and its reindex backfill. `pytest -m contract` runs the `pz_repo_analyses` pair against a real database, and `pytest -m rls` the member-write probe.

## Known edges

The gate identifies an imported project as one with `repo_url` set before `repo_created`. A from-scratch project caught in the crash window — `repo_url` recorded, lifecycle still `tech_review` — therefore also reads as imported to the Planner until its retry completes. It is rare, it is recoverable (the analysis endpoint works against that repository like any other), and closing it properly would need a durable "imported" marker on the project row, which this plan chose not to add.
