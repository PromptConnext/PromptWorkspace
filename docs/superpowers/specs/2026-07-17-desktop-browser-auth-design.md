# Desktop browser-auth handoff — implementation spec

Status: Approved 2026-07-17 · ADR: 0014

## Goal

Replace the desktop's native email/password cloud login with a browser-based
sign-in against the hosted `apps/web` auth pages, returning the Supabase session
to the desktop via a `promptconnext://` deep link and a short-lived one-time code
brokered through `apps/cloud`. Enables OAuth/magic-link/MFA and collapses auth to
a single UI. See ADR 0014 for rationale.

Scope covers four surfaces: `apps/web`, `apps/cloud`, `apps/engine`,
`apps/desktop`. Stub auth mode is out of scope (keeps its typed `X-User-Id`).

## Flow (happy path)

1. User clicks "Sign in with browser" in desktop `CloudConnect`.
2. Webview → engine `POST /engine/cloud/login/browser` → engine generates
   `state` (crypto random, stored in memory keyed by nothing — single pending
   login per install) and returns the URL to open, or the engine asks the Tauri
   shell to open it. Engine opens `${CLOUD_WEB_URL}/login?desktop=1&state=<state>`
   in the system browser.
3. Web login page detects `desktop=1`, runs the normal Supabase sign-in (any
   method). On an established session, it POSTs `{ refresh_token, state }` with
   the access token as Bearer to cloud `POST /desktop-auth/handoff`.
4. Cloud validates the JWT, mints `handoff_code` (opaque, single-use, TTL ~120s),
   stores `{ code → { refresh_token, user_id } }`, returns `{ code }`.
5. Web redirects the browser to `promptconnext://auth/callback?code=<code>&state=<state>`.
6. Desktop deep-link handler receives the URL, checks `state` matches the pending
   login, forwards `code` to engine `POST /engine/cloud/login/redeem`.
7. Engine calls cloud `POST /desktop-auth/redeem { code }` → cloud returns
   `{ access_token, refresh_token, user_id }` and deletes the code. Engine stores
   the session in the keychain (`cloud.session`) + SQLite app-state, exactly as
   `storeCloudSession` does today.
8. Engine emits its existing session-changed signal; `CloudConnect` reflects the
   signed-in user.

## Per-surface work

### apps/web
- `(auth)/login/page.tsx`: when `?desktop=1&state=` present, after a successful
  Supabase session, POST to cloud handoff, then `window.location.href =
  promptconnext://auth/callback?code=…&state=…`. Applies to any sign-in method
  (email/pw, OAuth callback landing, magic-link landing) — hook into the auth
  state, not just the password submit.
- Register/forgot/reset already redirect to login after completion; carry the
  `desktop=1&state=` query through so a user who registers in the desktop flow
  still hands off. (Preserve query params on the cross-links.)
- New config: `CLOUD_API_URL` already exists; no new env.

### apps/cloud
- New router `api/desktop_auth.py` mounted in `main.py`:
  - `POST /desktop-auth/handoff` — auth required (normal `get_current_user`);
    body `{ refresh_token, state }`; returns `{ code }`.
  - `POST /desktop-auth/redeem` — **no** user auth (the code IS the credential);
    body `{ code }`; returns `{ access_token, refresh_token, user_id }` or 404.
- Code store: in-process dict with expiry (single-instance, like presence).
  Single-use: delete on redeem. TTL sweep on access is enough.
- The access token returned by redeem: cloud can re-derive it from the refresh
  token via Supabase token endpoint, or the handoff can also stash the access
  token. Simpler: store both refresh + access at handoff, return both at redeem.

### apps/engine
- `routes/cloud.ts`: add `POST /engine/cloud/login/browser` (start: make/att
  store `state`, return `{ url, state }` or trigger open) and
  `POST /engine/cloud/login/redeem` (body `{ code }` → cloud redeem → store
  session). Remove/deprecate the supabase branch of the existing
  `POST /engine/cloud/login` password path.
- `cloudClient.ts`: add `redeemDesktopCode(code)` calling cloud; reuse
  `storeCloudSession`. Drop `supabasePasswordLogin` (or keep dead-flagged until
  desktop is migrated).
- Config: add `CLOUD_WEB_URL` (default the hosted web origin) so the engine knows
  where to point the browser.

### apps/desktop
- Add `tauri-plugin-deep-link`; register `promptzone` scheme (tauri.conf +
  per-OS: macOS `CFBundleURLTypes`, Windows registry via plugin, Linux .desktop).
- Rust: on deep-link event, parse `promptconnext://auth/callback`, pass `code` +
  `state` to the webview (event) or straight to a Tauri command that calls the
  engine redeem route.
- `CloudConnect.tsx`: replace the supabase email/password form with a single
  "Sign in with browser" button → engine `login/browser`; keep the stub-mode
  user-id form unchanged. Show a "waiting for browser…" state until the deep link
  returns.
- `api.ts`: bindings for the new engine routes.

## Security

- Only the opaque single-use `handoff_code` travels the deep link; TTL ≤ 120s,
  deleted on first redeem.
- `state` generated by the engine, verified on callback — rejects injected/replayed
  callbacks not tied to a pending local login.
- Redeem endpoint is unauthenticated by design (code is the bearer of identity);
  it must be strictly single-use and short-TTL, and return 404 on any miss.
- `promptconnext://` may be registered by other local apps; that is exactly why no
  long-lived token is ever placed in the callback URL (ADR 0014).
- Engine keychain storage path is unchanged; `authHeaders`/sync untouched.

## Out of scope / YAGNI

- Stub-mode changes (typed `X-User-Id` stays).
- Refresh-token rotation handling beyond what `cloudClient` already does.
- Multi-account per install (single pending login, single stored session — as today).
- Linux keychain (already unimplemented; not regressed here).

## Verification

- Web: unit-check the desktop query passthrough + handoff POST fires on session.
- Cloud: pytest for handoff→redeem happy path, single-use (second redeem 404),
  TTL expiry, redeem of unknown code 404, handoff rejects bad JWT.
- Engine: route redeem stores session; state mismatch rejected.
- Manual E2E: desktop button → browser → sign in → land back signed in. Requires a
  real Supabase project + registered scheme; note if unrunnable in-sandbox.
